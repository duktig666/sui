## 🎯 核心发现

### V2 原方案为何不可行

| 问题 | 预期 | 实际 | 结论 |
|-----|------|------|------|
| **冲突率** | < 5% | **30-50%** | 10x 差距 ❌ |
| **市价单冲突** | 低 | **70-90%** | 几乎必然冲突 ❌ |
| **撮合确定性** | 高 | **低** | 结果不可预测 ❌ |
| **用户体验** | 改善 | **变差** | 频繁回滚通知 ❌ |

**根本原因**:
> 订单簿的全局共享特性与乐观执行的局部性假设矛盾

```
CLOB 特性:
✗ 全局唯一订单簿（所有交易竞争）
✗ 高度耦合状态
✗ 顺序敏感（价格-时间优先）

乐观执行假设:
✓ 交易相对独立
✓ 冲突率低 < 5%
✓ 局部状态修改

结论: 不匹配 → V2 原方案不可行
```

### V2.1 如何解决问题

**核心思路**: 不强求提前执行，而是优化用户感知

| 方面 | V2 原案 | V2.1 解决方案 |
|-----|---------|--------------|
| **延迟优化** | 乐观执行（提前执行） | 预测引擎（提前展示） |
| **准确性** | 50% 回滚率 ❌ | 100% 准确 ✅ |
| **用户感知** | 快但不稳定 | 快速+透明 ✅ |
| **实现复杂度** | 极高（依赖图、MVCC） | 中等 ✅ |

## 🎓 关键技术洞察

### 1. 业务特性决定技术选型

**CLOB 的特殊性**:
- 全局共享订单簿（热点资源）
- 所有交易相互影响
- 顺序高度敏感
- → **不适合乐观执行**

**适合乐观执行的场景**:
- 交易相对独立（如账户间转账）
- 状态局部修改
- 冲突率低 < 5%

### 2. 用户体验 ≠ 执行速度

**错误思路**:
- 用户体验差 → 必须加快执行速度

**正确思路**:
- 用户体验差 → 优化用户感知 + 管理预期
- 快速反馈 + 透明信息 + 准确结果 = 好的用户体验

**V2.1 的启示**:
```
立即返回预测 (50ms)
+ 显示队列位置和预计时间（透明）
+ 后台准确确认 (400ms)
= 比 V2 更好的用户体验（零回滚）
```

### 3. 预测 vs 执行

| 维度 | 预测 | 乐观执行 |
|-----|------|---------|
| **目的** | 提供用户参考 | 提前完成交易 |
| **准确性要求** | 高置信度即可 | 必须 100% 准确 |
| **错误代价** | 用户更新认知 | 回滚+重执行+通知 |
| **状态影响** | 无（只读） | 有（修改 Pending State） |
| **复杂度** | 低（无状态） | 高（状态管理、回滚） |

**V2.1 选择预测的原因**:
- ✅ 低复杂度（无状态，只读）
- ✅ 低风险（错误代价小）
- ✅ 高准确度（85%+ 准确）
- ✅ 好体验（透明 + 快速反馈）

| **透明化队列** | 管理用户预期，提升感知体验 |
