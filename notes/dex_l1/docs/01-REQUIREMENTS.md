## 1. 概述 / Overview

### 1.1 项目背景 / Project Background

DEX L1 是基于 Sui 区块链 Fork 的原生去中心化交易所，通过在验证者节点内嵌原生撮合引擎，实现链上订单簿交易的极致性能。

**核心价值主张**：
- 链上订单簿 + CEX 级性能
- 完全去中心化 + 无需信任
- Sui 生态兼容 + Move 智能合约

### 1.2 术语定义 / Glossary

| 术语 | 定义 |
|-----|------|
| DEX | Decentralized Exchange，去中心化交易所 |
| Sequencer | 交易排序器，负责确定交易执行顺序 |
| Matching Engine | 撮合引擎，执行订单匹配 |
| WAL | Write-Ahead Log，写前日志 |
| Soft Confirmation | 软确认，Sequencer 确认（见 ADR-006） |
| Hard Confirmation | 硬确认，2f+1 验证者确认（见 ADR-006） |

### 1.3 指标口径表 / Metrics Definition Table

> **重要**：本节定义各性能指标的测量口径，消除歧义。

| 指标名称 | 测量起点 | 测量终点 | 目标值 | 说明 |
|---------|---------|---------|-------|------|
| **端到端延迟** | 订单到达 Sequencer | Soft Confirmation 返回客户端 | < 50ms P99 | 用户感知延迟 |
| **单次撮合延迟** | 调用 `Engine::match_order()` | 函数返回 | < 10μs P99 | 纯撮合算法，不含 I/O |
| **撮合路径延迟** | Sequencer 收到订单 | 撮合完成 + 状态更新 | ~15ms | 含序列号分配、撮合、内存状态更新 |
| **持久化延迟** | WAL 写入开始 | fsync 完成 | ~10-20ms | 依赖硬件（NVMe SSD） |
| **软确认延迟** | 订单到达 | Sequencer 返回确认 | < 50ms | 异步持久化，不保证 fsync |
| **硬确认延迟** | 订单到达 | 2f+1 durable ack | < 100ms | 同步 fsync，RPO=0 |

**口径关系图**：

```
订单到达
    │
    ├── [~5ms] Sequencer 排序 ──┐
    │                           │
    ├── [<10μs] 单次撮合 ◄──────┤ 撮合路径 ~15ms
    │                           │
    ├── [~5ms] 状态更新 ────────┘
    │
    ├── [~20ms] 广播 + 回复 ────── 软确认 < 50ms
    │
    ├── [~10-20ms] WAL fsync ───┐
    │                           │
    └── [~15ms] 2f+1 投票收集 ──┴── 硬确认 < 100ms
```

**注意**：
- "单次撮合" 指纯算法操作，< 10μs
- "撮合路径" 指从收到订单到撮合完成的整体贡献，~15ms
- 两者不矛盾：一次撮合路径可能触发多次单次撮合（部分成交）

## 2. 功能需求 / Functional Requirements

### 2.1 核心基础设施 / Core Infrastructure (FR-CORE)

#### FR-CORE-001: 交易排序
- **描述**: 系统必须提供确定性的交易排序机制
- **验收标准**: 所有验证者对相同交易集合产生相同的排序结果
- **优先级**: P0

#### FR-CORE-002: 订单撮合
- **描述**: 系统必须实现价格-时间优先的撮合算法
- **验收标准**: 相同价格的订单按时间顺序成交
- **优先级**: P0

#### FR-CORE-003: 状态持久化
- **描述**: 系统必须保证状态的持久化和可恢复性
- **验收标准**: 节点重启后能恢复到最新一致状态
- **优先级**: P0

#### FR-CORE-004: 双确认机制
- **描述**: 系统必须支持软确认和硬确认两种确认模式
- **验收标准**:
  - 软确认：Sequencer 确认后返回
  - 硬确认：2f+1 验证者确认后最终确定
- **优先级**: P0

### 2.2 账户管理 / Account Management (FR-ACCOUNT)

#### FR-ACCOUNT-001: 余额管理
- **描述**: 系统必须支持用户资产余额的增减操作
- **验收标准**: 余额变更具有原子性，不会出现负余额
- **优先级**: P0

#### FR-ACCOUNT-002: 存款操作
- **描述**: 用户必须能够将 Sui 链上资产存入 DEX
- **验收标准**: 存款完成后余额正确更新
- **优先级**: P0

#### FR-ACCOUNT-003: 取款操作
- **描述**: 用户必须能够将 DEX 余额提取到 Sui 链上
- **验收标准**: 取款后链上资产和 DEX 余额一致
- **优先级**: P0

#### FR-ACCOUNT-004: 余额锁定
- **描述**: 下单时必须锁定对应资产
- **验收标准**: 可用余额 = 总余额 - 锁定余额
- **优先级**: P0

### 2.3 市场管理 / Market Management (FR-MARKET)

#### FR-MARKET-001: 市场创建
- **描述**: 管理员必须能够创建新的交易市场
- **验收标准**: 市场创建后可以接受订单
- **优先级**: P0

#### FR-MARKET-002: 市场参数配置
- **描述**: 系统必须支持配置市场参数
- **参数列表**:
  - `tick_size`: 最小价格变动单位
  - `step_size`: 最小数量变动单位
  - `min_order_size`: 最小订单金额
  - `maker_fee`: Maker 手续费率
  - `taker_fee`: Taker 手续费率
- **优先级**: P0

#### FR-MARKET-003: 市场状态控制
- **描述**: 管理员必须能够暂停/恢复市场交易
- **验收标准**: 暂停状态下拒绝新订单，但允许撤单
- **优先级**: P1

### 2.4 现货交易 / Spot Trading (FR-SPOT)

#### FR-SPOT-001: 限价单
- **描述**: 用户必须能够提交指定价格的限价单
- **验收标准**: 订单按指定价格或更优价格成交
- **优先级**: P0

#### FR-SPOT-002: 市价单
- **描述**: 用户必须能够提交立即成交的市价单
- **验收标准**: 订单按当前最优价格立即成交
- **优先级**: P0

#### FR-SPOT-003: IOC 订单
- **描述**: Immediate-Or-Cancel，未成交部分立即取消
- **验收标准**: 订单提交后立即尝试成交，未成交部分取消
- **优先级**: P1

#### FR-SPOT-004: FOK 订单
- **描述**: Fill-Or-Kill，全部成交或全部取消
- **验收标准**: 订单要么全部成交，要么全部取消
- **优先级**: P1

#### FR-SPOT-005: Post-Only 订单
- **描述**: 仅挂单，不吃单
- **验收标准**: 如果订单会立即成交则拒绝
- **优先级**: P1

#### FR-SPOT-006: 订单取消
- **描述**: 用户必须能够取消未成交的订单
- **验收标准**: 取消后释放锁定余额
- **优先级**: P0

#### FR-SPOT-007: 批量撤单
- **描述**: 用户必须能够批量取消订单
- **验收标准**: 支持按市场/按方向批量撤单
- **优先级**: P1

### 2.5 永续合约 / Perpetual Contracts (FR-PERP)

> 永续合约为 Phase 2 实现，此处仅列出概要需求

#### FR-PERP-001: 保证金管理
- **描述**: 支持初始保证金和维持保证金机制
- **优先级**: P2

#### FR-PERP-002: 资金费率
- **描述**: 实现资金费率计算和结算
- **优先级**: P2

#### FR-PERP-003: 强制平仓
- **描述**: 保证金不足时触发强制平仓
- **优先级**: P2

#### FR-PERP-004: 保险基金
- **描述**: 维护保险基金用于穿仓损失
- **优先级**: P2

### 2.6 管理功能 / Administration (FR-ADMIN)

#### FR-ADMIN-001: 手续费配置
- **描述**: 管理员必须能够配置手续费率
- **优先级**: P1

#### FR-ADMIN-002: 风控参数配置
- **描述**: 管理员必须能够配置风控参数
- **参数**: 价格带宽、单笔限额、账户限额
- **优先级**: P1

#### FR-ADMIN-003: 紧急暂停
- **描述**: 管理员必须能够紧急暂停系统
- **优先级**: P0

## 3. 非功能需求 / Non-Functional Requirements

### 3.1 性能需求 / Performance (NFR-PERF)

#### NFR-PERF-001: 端到端延迟
| 指标 | 目标值 | 测量方式 |
|-----|-------|---------|
| P50 | < 20ms | 订单提交到软确认 |
| P99 | < 50ms | 订单提交到软确认 |
| P99.9 | < 100ms | 订单提交到软确认 |

#### NFR-PERF-002: 撮合延迟
| 指标 | 目标值 | 测量方式 |
|-----|-------|---------|
| P50 | < 5μs | 单次撮合操作 |
| P99 | < 10μs | 单次撮合操作 |

#### NFR-PERF-003: 吞吐量
| 指标 | 目标值 | 条件 |
|-----|-------|------|
| 峰值 TPS | ≥ 200,000 | 单市场 |
| 持续 TPS | ≥ 100,000 | 多市场并行 |

#### NFR-PERF-004: 确认延迟
| 类型 | 目标值 | 说明 |
|-----|-------|------|
| 软确认 | < 50ms | Sequencer 确认 |
| 硬确认 | < 100ms | 2f+1 验证者确认 |

### 3.2 可用性需求 / Availability (NFR-AVAIL)

#### NFR-AVAIL-001: 系统可用性
- **目标**: ≥ 99.9% (年度)
- **计算**: 排除计划维护时间

#### NFR-AVAIL-002: 故障切换时间
- **目标**: < 100ms
- **场景**: Sequencer 故障切换

#### NFR-AVAIL-003: 恢复时间目标 (RTO)
- **目标**: < 5 分钟
- **场景**: 节点崩溃重启

#### NFR-AVAIL-004: 恢复点目标 (RPO)
- **目标**: RPO=0 **仅适用于 Hard Confirmation**（见 `02-ARCHITECTURE-OVERVIEW.md` ADR-006）
- **说明**:
  - Hard Confirmation (2f+1 durable ack): RPO=0，零数据丢失
  - Soft Confirmation: 不保证 RPO，异步持久化存在极小丢失窗口
- **机制**: WAL + 2f+1 同步 fsync

### 3.3 安全需求 / Security (NFR-SEC)

#### NFR-SEC-001: 交易签名验证
- **要求**: 所有交易必须经过签名验证
- **算法**: Ed25519 / Secp256k1

#### NFR-SEC-002: 防重放攻击
- **要求**: 系统必须防止交易重放
- **机制**: Nonce / 序列号

#### NFR-SEC-003: 余额安全
- **要求**: 余额操作必须原子性
- **验证**: 总余额守恒

#### NFR-SEC-004: 访问控制
- **要求**: 管理功能必须有权限控制
- **机制**: 多签 / 治理

### 3.4 兼容性需求 / Compatibility (NFR-COMPAT)

#### NFR-COMPAT-001: Sui 钱包兼容
- **要求**: 支持标准 Sui 钱包连接
- **钱包**: Sui Wallet, Suiet, Ethos 等

#### NFR-COMPAT-002: RPC 兼容
- **要求**: 保持 Sui JSON-RPC 兼容
- **扩展**: 添加 DEX 专用 RPC 方法

#### NFR-COMPAT-003: Move 合约兼容
- **要求**: 支持标准 Move 智能合约执行
- **限制**: DEX 操作走原生路径

### 3.5 可扩展性需求 / Scalability (NFR-SCALE)

#### NFR-SCALE-001: 市场数量
- **目标**: 支持 ≥ 1000 个交易市场

#### NFR-SCALE-002: 并发用户
- **目标**: 支持 ≥ 100,000 并发连接

#### NFR-SCALE-003: 订单簿深度
- **目标**: 单市场支持 ≥ 1,000,000 挂单

## 4. 用例场景 / Use Cases

### UC-001: 现货限价买入

**参与者**: 交易者
**前置条件**: 用户已存入足够的报价资产
**主流程**:
1. 用户提交限价买单 (市场: BTC-USDT, 价格: 50000, 数量: 0.1)
2. 系统验证签名和余额
3. Sequencer 分配序列号
4. 撮合引擎检查是否有匹配卖单
5. 如果匹配，生成成交记录并更新余额
6. 如果不匹配，订单进入订单簿
7. 返回软确认

**后置条件**: 订单成交或挂单成功

### UC-002: 现货市价卖出

**参与者**: 交易者
**前置条件**: 用户持有足够的基础资产
**主流程**:
1. 用户提交市价卖单 (市场: BTC-USDT, 数量: 0.1)
2. 系统验证签名和余额
3. Sequencer 分配序列号
4. 撮合引擎按最优价格成交
5. 生成成交记录并更新余额
6. 返回软确认

**后置条件**: 订单全部或部分成交

### UC-003: 订单取消

**参与者**: 交易者
**前置条件**: 用户有未成交的挂单
**主流程**:
1. 用户提交撤单请求 (订单ID)
2. 系统验证签名和订单所有权
3. Sequencer 分配序列号
4. 从订单簿移除订单
5. 释放锁定余额
6. 返回软确认

**后置条件**: 订单已取消，余额已释放

### UC-004: 资产存款

**参与者**: 用户
**前置条件**: 用户 Sui 钱包有足够资产
**主流程**:
1. 用户调用存款 Move 合约
2. 合约锁定用户资产
3. DEX 引擎更新用户余额
4. 返回存款确认

**后置条件**: DEX 余额增加，链上资产减少

### UC-005: 资产取款

**参与者**: 用户
**前置条件**: 用户 DEX 余额充足
**主流程**:
1. 用户提交取款请求
2. 系统验证签名和余额
3. DEX 引擎扣减余额
4. 触发 Move 合约释放资产
5. 资产转入用户钱包

**后置条件**: DEX 余额减少，链上资产增加

### UC-006: Sequencer 故障切换

**参与者**: 系统
**前置条件**: 主 Sequencer 故障
**主流程**:
1. 验证者检测到心跳超时 (50ms)
2. 发起 Leader 切换投票
3. 达到 2f+1 投票
4. 新 Leader 同步状态
5. 恢复服务

**后置条件**: 新 Sequencer 接管，服务恢复

## 6. 约束与假设 / Constraints & Assumptions

### 6.1 约束 / Constraints

1. **Sui Fork 约束**: 必须基于 Sui 代码库，最小化修改
2. **性能约束**: 50ms 端到端延迟，200K TPS
3. **兼容性约束**: 保持 Sui 钱包和 RPC 兼容
4. **安全约束**: 不能有单点故障

### 6.2 假设 / Assumptions

1. **网络假设**: 验证者之间网络延迟 < 10ms
2. **硬件假设**: NVMe SSD，≥ 32GB RAM，≥ 8 核 CPU
3. **负载假设**: 80% 订单为限价单
4. **用户假设**: 用户接受软确认风险

## 7. 风险分析 / Risk Analysis

| 风险 | 影响 | 概率 | 缓解措施 |
|-----|------|-----|---------|
| Sequencer 单点故障 | 高 | 中 | HA 机制 + 快速切换 |
| 撮合引擎性能不足 | 高 | 低 | 无锁设计 + 批量处理 |
| Sui 上游更新冲突 | 中 | 高 | 最小化修改 + 抽象层 |
| 状态不一致 | 高 | 低 | WAL + 校验和 |
| 安全漏洞 | 高 | 中 | 审计 + 形式化验证 |
