## 1. 概述 / Overview

### 1.1 设计目标 / Design Goals

1. **极致性能**: 50ms 端到端延迟，200K TPS
2. **去中心化**: 复用 Sui 验证者网络，无单点信任
3. **兼容性**: 保持 Sui 钱包、RPC、Move 合约兼容
4. **可维护性**: 最小化 Sui Fork 修改，便于上游同步

### 1.2 核心创新 / Key Innovations

```
传统 DEX (Move VM):     ~600ms 延迟，~1000 TPS
DEX L1 (Native Engine): ~50ms 延迟，~200K TPS
```

**性能提升关键**：
- 绕过 Move VM，原生 Rust 撮合
- 中心化 Sequencer，去中心化验证
- 内存状态 + 异步持久化

## 3. 数据流设计 / Data Flow

### 3.1 DEX 快速路径 / DEX Fast Path (< 50ms)

```
User                Sequencer           Engine              Storage
  │                     │                  │                    │
  │ ─── Order ────────► │                  │                    │
  │                     │ ── Assign Seq ─► │                    │
  │                     │                  │ ── Update State ─► │
  │                     │                  │ ◄── Ack ────────── │
  │                     │ ◄─ Match Result ─│                    │
  │ ◄── Soft Confirm ── │                  │                    │
  │                     │                  │                    │
  │     ═══════ Async Broadcast to Validators ═══════          │
  │                     │                  │                    │
  │ ◄── Hard Confirm ── │ (2f+1 votes)     │                    │
```

**时间分解**：
- T0: 用户提交订单
- T0+5ms: Sequencer 分配序列号
- T0+15ms: 撮合完成
- T0+25ms: 状态更新
- T0+35ms: 软确认返回
- T0+100ms: 硬确认 (2f+1)

## 4. 架构决策记录 / Architecture Decision Records

### AD-001: 中心化 Sequencer vs 完全共识

**背景/Context**:
需要在性能和去中心化之间权衡。完全共识需要 ~600ms，无法满足 50ms 目标。

**备选方案/Options**:
1. 完全 Mysticeti 共识：~600ms 延迟
2. 中心化 Sequencer + 异步验证：~50ms 软确认
3. 多 Sequencer 轮换：~100ms 延迟

**决策/Decision**:
选择方案 2：中心化 Sequencer + 异步验证

**理由/Rationale**:
- 满足 50ms 延迟目标
- 软确认满足大部分交易场景
- 硬确认提供最终确定性

**权衡/Trade-offs**:
- (+) 极低延迟
- (+) 高吞吐量
- (-) 软确认期间存在理论风险
- (-) Sequencer 成为性能瓶颈

---

### AD-002: 原生 Rust 引擎 vs Move VM

**背景/Context**:
Move VM 执行开销大，无法达到目标性能。

**备选方案/Options**:
1. 纯 Move VM：安全但慢
2. Move Precompile：中等性能
3. 原生 Rust 引擎：最高性能

**决策/Decision**:
选择方案 3：原生 Rust 引擎

**理由/Rationale**:
- 撮合延迟 < 10μs，Move VM 无法达到
- 直接内存操作，无 VM 开销
- 可以使用 SIMD 等底层优化

**权衡/Trade-offs**:
- (+) 极致性能
- (+) 完全控制执行流程
- (-) 需要单独的安全审计
- (-) 与 Move 生态分离

---

### AD-003: 复用验证者网络 vs 独立 HA 集群

**背景/Context**:
Sequencer 需要高可用，可以自建集群或复用 Sui 验证者。

**备选方案/Options**:
1. 独立 HA 集群：完全独立
2. 复用验证者网络：共享基础设施
3. 混合模式：独立 Sequencer + 验证者确认

**决策/Decision**:
选择方案 2：复用验证者网络

**理由/Rationale**:
- 利用现有 stake-weighted 信任模型
- 复用 Mysticeti 的 Leader 选举逻辑
- 减少运维复杂度

**权衡/Trade-offs**:
- (+) 复用成熟基础设施
- (+) 共享安全模型
- (-) 受限于验证者数量
- (-) 网络依赖

---

### AD-004: 内存状态 + WAL vs 纯 RocksDB

**背景/Context**:
状态存储需要平衡性能和持久性。

**备选方案/Options**:
1. 纯 RocksDB：可靠但慢
2. 内存 + 同步 WAL：快速但复杂
3. 内存 + 异步 WAL：最快但有风险

**决策/Decision**:
选择方案 2：内存状态 + 同步 WAL

**理由/Rationale**:
- 内存操作保证性能
- WAL 保证持久性
- 同步写入防止数据丢失

**权衡/Trade-offs**:
- (+) 高性能读取
- (+) 持久性保证
- (-) WAL 写入延迟
- (-) 恢复需要重放

---

### AD-005: Precompile 桥接 vs Native Functions

**背景/Context**:
需要在 Move 合约和原生引擎之间建立桥梁。

**备选方案/Options**:
1. Move Native Functions：修改 Move VM
2. Precompile 机制：交易拦截
3. 独立 RPC：完全分离

**决策/Decision**:
选择方案 2：Precompile 机制

**理由/Rationale**:
- 不修改 Move VM 核心
- 通过特定合约地址触发
- 保持 Move 语义完整

**权衡/Trade-offs**:
- (+) 不侵入 Move VM
- (+) 清晰的调用边界
- (-) 需要特殊合约
- (-) 跨边界调用复杂

### 5.2 攻击面分析 / Attack Surface

| 攻击向量 | 风险等级 | 缓解措施 |
|---------|---------|---------|
| Sequencer 作恶 | 中 | 硬确认验证 + 快速切换 |
| 重放攻击 | 低 | Nonce + 序列号 |
| 抢跑交易 | 中 | 加密提交 + 延迟揭示 |
| 余额篡改 | 高 | 状态校验 + 审计日志 |
| DoS 攻击 | 中 | 限流 + 费用机制 |
