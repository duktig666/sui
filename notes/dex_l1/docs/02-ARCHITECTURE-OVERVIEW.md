## 1. 概述 / Overview

### 1.1 设计目标 / Design Goals

1. **极致性能**: 50ms 端到端延迟，200K TPS
2. **去中心化**: 复用 Sui 验证者网络，无单点信任
3. **兼容性**: 保持 Sui 钱包、RPC、Move 合约兼容
4. **可维护性**: 最小化 Sui Fork 修改，便于上游同步

### 1.2 核心创新 / Key Innovations

```
传统 DEX (Move VM):     ~600ms 延迟，~1000 TPS
DEX L1 (Native Engine): ~50ms 延迟，~200K TPS
```

**性能提升关键**：
- 绕过 Move VM，原生 Rust 撮合
- 中心化 Sequencer，去中心化验证
- 内存状态 + 异步持久化

### 2.2 组件职责 / Component Responsibilities

| 组件 | 职责 | 延迟贡献 | 说明 |
|-----|------|---------|------|
| Transaction Router | 交易分类与路由 | ~1ms | |
| Sequencer | 交易排序、序列号分配 | ~5ms | |
| Matching Engine | 订单撮合、余额更新 | ~10ms (路径) | 单次撮合 < 10μs，路径含状态更新 |
| DEX State | 内存状态管理 | ~5ms | |
| WAL | 写前日志持久化 | ~10ms (异步) | Hard 需 fsync |
| Consensus | 验证者确认 | ~20ms | 仅 Hard Confirmation |

> **指标说明**：Matching Engine 的 ~10ms 是"撮合路径"贡献（含序列分配后的执行和状态更新），
> 而非"单次撮合"操作（< 10μs）。详见 `01-REQUIREMENTS.md` 1.3 指标口径表。

### 3.1 DEX 快速路径 / DEX Fast Path (< 50ms)

```
User                Sequencer           Engine              Storage
  │                     │                  │                    │
  │ ─── Order ────────► │                  │                    │
  │                     │ ── Assign Seq ─► │                    │

  │ ◄── Soft Confirm ── │                  │                    │
  │                     │                  │                    │
  │     ═══════ Async Broadcast to Validators ═══════          │
  │                     │                  │                    │
  │ ◄── Hard Confirm ── │ (2f+1 votes)     │                    │

**时间分解**：
- T0: 用户提交订单

- T0+35ms: 软确认返回
- T0+100ms: 硬确认 (2f+1)

## 4. 架构决策记录 / Architecture Decision Records

### AD-001: 中心化 Sequencer vs 完全共识

**背景/Context**:
需要在性能和去中心化之间权衡。完全共识需要 ~600ms，无法满足 50ms 目标。

**备选方案/Options**:
1. 完全 Mysticeti 共识：~600ms 延迟
2. 中心化 Sequencer + 异步验证：~50ms 软确认
3. 多 Sequencer 轮换：~100ms 延迟

**决策/Decision**:
选择方案 2：中心化 Sequencer + 异步验证

**理由/Rationale**:
- 满足 50ms 延迟目标
- 软确认满足大部分交易场景
- 硬确认提供最终确定性

**权衡/Trade-offs**:
- (+) 极低延迟
- (+) 高吞吐量
- (-) 软确认期间存在理论风险
- (-) Sequencer 成为性能瓶颈

---

### AD-002: 原生 Rust 引擎 vs Move VM

**背景/Context**:
Move VM 执行开销大，无法达到目标性能。

**备选方案/Options**:
1. 纯 Move VM：安全但慢
2. Move Precompile：中等性能
3. 原生 Rust 引擎：最高性能

**决策/Decision**:
选择方案 3：原生 Rust 引擎

**理由/Rationale**:
- 撮合延迟 < 10μs，Move VM 无法达到
- 直接内存操作，无 VM 开销
- 可以使用 SIMD 等底层优化

**权衡/Trade-offs**:
- (+) 极致性能
- (+) 完全控制执行流程
- (-) 需要单独的安全审计
- (-) 与 Move 生态分离

---

### AD-003: 复用验证者网络 vs 独立 HA 集群

**背景/Context**:
Sequencer 需要高可用，可以自建集群或复用 Sui 验证者。

**备选方案/Options**:
1. 独立 HA 集群：完全独立
2. 复用验证者网络：共享基础设施
3. 混合模式：独立 Sequencer + 验证者确认

**决策/Decision**:
选择方案 2：复用验证者网络

**理由/Rationale**:
- 利用现有 stake-weighted 信任模型
- 复用 Mysticeti 的 Leader 选举逻辑
- 减少运维复杂度

**权衡/Trade-offs**:
- (+) 复用成熟基础设施
- (+) 共享安全模型
- (-) 受限于验证者数量
- (-) 网络依赖

---

### AD-004: 内存状态 + WAL vs 纯 RocksDB

**背景/Context**:
状态存储需要平衡性能和持久性。

**备选方案/Options**:
1. 纯 RocksDB：可靠但慢
2. 内存 + 同步 WAL：快速但复杂
3. 内存 + 异步 WAL：最快但有风险

**决策/Decision**:
选择方案 2：内存状态 + 同步 WAL

**理由/Rationale**:
- 内存操作保证性能
- WAL 保证持久性
- 同步写入防止数据丢失

**权衡/Trade-offs**:
- (+) 高性能读取
- (+) 持久性保证
- (-) WAL 写入延迟
- (-) 恢复需要重放

---

### AD-005: Precompile 桥接 vs Native Functions

**背景/Context**:
需要在 Move 合约和原生引擎之间建立桥梁。

**备选方案/Options**:
1. Move Native Functions：修改 Move VM
2. Precompile 机制：交易拦截
3. 独立 RPC：完全分离

**决策/Decision**:
选择方案 2：Precompile 机制

**理由/Rationale**:
- 不修改 Move VM 核心
- 通过特定合约地址触发
- 保持 Move 语义完整

**权衡/Trade-offs**:
- (+) 不侵入 Move VM
- (+) 清晰的调用边界
- (-) 需要特殊合约
- (-) 跨边界调用复杂

---

### AD-006: 确认语义与持久化等级 / Confirmation Semantics & Durability

**背景/Context**:
DEX 需要平衡延迟和数据安全。需要明确定义不同确认级别的语义、持久化保证和 RPO 承诺。

**核心定义 / Core Definitions**:

| 确认级别 | 定义 | 延迟目标 | 持久化 | RPO |
|---------|------|---------|--------|-----|
| **Soft Confirmation** | Sequencer 已接收并执行 | < 50ms | 异步（无保证） | 不承诺 |
| **Hard Confirmation** | 2f+1 验证者 durable ack | < 100ms | 同步（fsync 完成） | = 0 |

**关键语义 / Key Semantics**:

1. **Soft Confirmation（软确认）**
   - 含义：Sequencer 已接收交易、分配序列号、完成撮合/状态更新
   - 持久化：异步 WAL 写入已启动，但不保证 fsync 完成
   - 风险：Sequencer 崩溃时可能丢失（概率极低，窗口 < 10ms）
   - 用途：大部分交易场景，低延迟优先

2. **Hard Confirmation（硬确认）**
   - 含义：2f+1 验证者已收到、验证、并 durable ack（fsync 完成）
   - 持久化：所有参与节点的 WAL 均已 fsync
   - 风险：仅 BFT 失效场景（> f 节点同时拜占庭）
   - 用途：最终一致性依据，客户端应以此为准

**实现要求 / Implementation Requirements**:

```
Hard Confirmation 100ms 预算分解:
├── Soft Confirmation:  ~35ms (见 3.1 节)
├── 网络广播:           ~20ms (并行发送)
├── 验证者接收+验证:    ~10ms
├── WAL fsync:          ~20ms (group commit)
├── 投票收集:           ~15ms (2f+1 即返回)
└── 总计:              ~100ms
```

**硬件/网络假设 / Hardware Assumptions**:

| 组件 | 要求 | 原因 |
|-----|------|-----|
| 存储 | NVMe SSD, fsync < 10ms | Hard confirmation 需要快速 fsync |
| 网络 | 10GbE+, RTT < 10ms | 验证者间通信延迟 |
| CPU | 高主频优先 | 签名验证、序列化 |

**客户端责任 / Client Responsibilities**:

1. **默认行为**：等待 Soft Confirmation 后即可更新 UI
2. **关键操作**：大额交易、提款等应等待 Hard Confirmation
3. **重试策略**：Soft 确认后若未收到 Hard 确认（超时），应查询状态或重试
4. **幂等设计**：客户端应使用 `clientOrderId` 保证幂等性

### 5.2 威胁建模 / Threat Modeling

> **注意**: 本节补充 GPT 评审 (design_review_gpt_20251231.md) 指出的安全模型缺失部分。

#### 5.2.1 攻击面矩阵 / Attack Surface Matrix

| 攻击向量 | 风险等级 | STRIDE 分类 | 缓解措施 | 详见 |
|---------|---------|------------|---------|------|
| **Sequencer 作恶** | 高 | Tampering, Elevation | 硬确认验证 + 快速切换 + 审计 | 5.2.2 |
| **MEV/抢跑** | 高 | Information Disclosure | Commit-Reveal + 批量撮合 | 5.2.3 |
| **DoS 攻击** | 高 | Denial of Service | 多层限流 + 费用机制 | 5.2.4 |
| **重放攻击** | 中 | Spoofing | Nonce + 序列号 + 过期时间 | 5.2.5 |
| **余额篡改** | 高 | Tampering | Merkle 证明 + 审计日志 | 5.2.6 |
| **密钥泄露** | 高 | Spoofing | HSM + 密钥轮换 + 多签 | 5.2.7 |

#### 5.2.2 Sequencer 作恶缓解 / Sequencer Misbehavior Mitigation

```
┌─────────────────────────────────────────────────────────────┐
│               Sequencer 作恶场景与缓解                       │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  作恶类型 1: 交易审查 (Censorship)                          │
│  ├── 检测: 客户端监控订单确认延迟                           │
│  ├── 缓解: 超时后可向其他验证者投诉                         │
│  └── 惩罚: 累计投诉触发 Leader 切换 + Slash                 │
│                                                              │
│  作恶类型 2: 交易重排序 (Reordering)                        │
│  ├── 检测: 比较 Soft/Hard 确认序列号                        │
│  ├── 缓解: 硬确认前交易可质疑                               │
│  └── 惩罚: 证明重排序后 Slash Sequencer Stake               │
│                                                              │
│  作恶类型 3: 交易插入 (Sandwich Attack)                     │
│  ├── 检测: 分析连续交易的地址模式                           │
│  ├── 缓解: Commit-Reveal 机制 (见 5.2.3)                    │
│  └── 惩罚: 链上证明后 Slash                                 │
│                                                              │
│  作恶类型 4: 双花尝试 (Double Spend)                        │
│  ├── 检测: 硬确认阶段验证者校验                             │
│  ├── 缓解: 2f+1 验证 + 序列号唯一性                         │
│  └── 惩罚: 即时 Slash + 永久禁止                            │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**安全不变量 (Sequencer)**:
1. 软确认的交易必须在硬确认中保持相同顺序
2. 同一序列号不能分配给两个不同交易
3. Sequencer 不能无限期延迟交易确认

#### 5.2.3 MEV/抢跑缓解 / MEV/Frontrunning Mitigation

```
┌─────────────────────────────────────────────────────────────┐
│               Commit-Reveal 防抢跑机制                       │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Phase 1: Commit (提交加密订单)                              │
│  ┌─────────────────────────────────────────────────────────┐│
│  │ Client:                                                  ││
│  │   secret = random_bytes(32)                              ││
│  │   commitment = hash(order || secret)                     ││
│  │   submit(commitment, encrypted_order)                    ││
│  └─────────────────────────────────────────────────────────┘│
│                           │                                  │
│                           ▼ (等待 N 个区块)                  │
│  Phase 2: Reveal (揭示订单)                                  │
│  ┌─────────────────────────────────────────────────────────┐│
│  │ Client:                                                  ││
│  │   reveal(order, secret)                                  ││
│  │                                                          ││
│  │ Sequencer:                                               ││
│  │   verify: hash(order || secret) == commitment            ││
│  │   if valid: execute(order)                               ││
│  └─────────────────────────────────────────────────────────┘│
│                                                              │
│  参数配置:                                                   │
│  • Commit 有效期: 10 个批次 (~50ms)                         │
│  • Reveal 窗口: 5 个批次 (~25ms)                            │
│  • 未揭示惩罚: 丢失 Commit 费用                             │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**批量撮合防抢跑**:
- 同一批次内的订单同时揭示、同时撮合
- 批次内排序使用 commitment hash 的字典序（不可预测）
- Sequencer 无法在批次形成后插入自己的订单

#### 5.2.4 DoS 防护 / DoS Protection

```
┌─────────────────────────────────────────────────────────────┐
│               多层 DoS 防护                                  │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Layer 1: 网络层                                             │
│  ├── 连接限制: 单 IP 最多 100 连接                          │
│  ├── 请求限流: 单连接 1000 req/s                            │
│  └── 黑名单: 恶意 IP 自动封禁 1h                            │
│                                                              │
│  Layer 2: 协议层                                             │
│  ├── 签名验证: 无效签名直接丢弃                             │
│  ├── 序列号检查: 重复/过期交易丢弃                          │
│  └── 大小限制: 单交易最大 10KB                              │
│                                                              │
│  Layer 3: 账户层                                             │
│  ├── 账户限流: 单账户 100 订单/s                            │
│  ├── 余额检查: 余额不足立即拒绝                             │
│  └── 挂单限制: 单账户最多 1000 挂单                         │
│                                                              │
│  Layer 4: 经济层                                             │
│  ├── Gas 费用: 每笔交易收取基础费用                         │
│  ├── 优先费用: 拥堵时支持加速费                             │
│  └── 取消费用: 频繁撤单收取惩罚费                           │
│                                                              │

#### 5.2.5 重放攻击防护 / Replay Attack Prevention

- **Nonce**: 每个账户维护单调递增 nonce
- **序列号**: Sequencer 分配全局唯一序列号
- **过期时间**: 交易包含 `valid_until` 字段，默认 5 分钟
- **跨链防护**: Intent Scope 包含 chain_id

#### 5.2.6 余额完整性 / Balance Integrity

- **Merkle 状态树**: 每个批次生成 state_root
- **余额证明**: 客户端可请求 Merkle 证明验证余额
- **审计日志**: 所有余额变更记录到 WAL
- **守恒检验**: 每批次验证 Σ(入金) - Σ(出金) = Δ(余额)
