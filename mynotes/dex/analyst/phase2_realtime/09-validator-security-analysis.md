# Validator RPC 暴露安全分析

> 创建日期: 2026-02-05
> 状态: 分析完成

## 1. 背景

自建 Validator 节点可以暴露 RPC，让 dex-realtime 直接订阅事件，延迟可达 400-600ms。但需要评估安全风险。

---

## 2. Validator 暴露 RPC 的安全风险

### 2.1 风险概览

```
┌─────────────────────────────────────────────────────────────────┐
│                      Validator 安全风险                          │
│                                                                 │
│   ┌───────────────────────────────────────────────────────┐     │
│   │                    Validator 节点                      │     │
│   │                                                       │     │
│   │   ┌─────────────┐    ┌─────────────┐                  │     │
│   │   │  共识模块    │←──│  RPC 服务   │←── 外部请求      │     │
│   │   │  (核心任务)  │   │  (额外负载)  │                  │     │
│   │   └─────────────┘    └─────────────┘                  │     │
│   │         ↑                   ↑                         │     │
│   │         │                   │                         │     │
│   │    资源竞争            攻击入口                        │     │
│   │                                                       │     │
│   └───────────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 具体风险分析

| 风险 | 严重程度 | 说明 |
|------|----------|------|
| **共识影响** | 🔴 高 | RPC 负载可能导致共识响应延迟，被踢出验证者集合 |
| **资源竞争** | 🟠 中 | 大量订阅连接消耗内存和 CPU |
| **攻击面** | 🟠 中 | RPC 是额外的攻击入口 |
| **质押风险** | 🔴 高 | Validator 掉线可能被 slash |
| **DDoS 攻击** | 🔴 高 | RPC 被攻击可能影响共识参与 |
| **侧信道攻击** | 🟡 低 | 通过 RPC 响应时间推断内部状态 |

### 2.3 风险场景

1. **DDoS 攻击**
   - 攻击者向 RPC 发送大量请求
   - CPU/内存/带宽被占用
   - 共识消息处理延迟
   - Validator 被判定为离线

2. **资源耗尽**
   - 大量 WebSocket 订阅连接
   - 内存持续增长
   - OOM 导致进程崩溃

3. **漏洞利用**
   - RPC 实现存在漏洞
   - 被攻击者利用获取权限
   - 影响共识私钥安全

---

## 3. 推荐方案：Validator + 索引节点分离

### 3.1 架构设计

```
┌─────────────────────────────────────────────────────────────────┐
│                    推荐架构：职责分离                            │
│                                                                 │
│   ┌───────────────────────────────────────────────────────┐     │
│   │                  Validator 节点                        │     │
│   │                                                       │     │
│   │   职责：只做共识，不对外暴露 RPC                        │     │
│   │                                                       │     │
│   │   ┌─────────────┐                                     │     │
│   │   │  共识模块    │ ← 专注共识，最高优先级               │     │
│   │   └──────┬──────┘                                     │     │
│   │          │                                            │     │
│   │          │ 内部通信（本地 IPC / 共享存储）              │     │
│   │          ↓                                            │     │
│   └──────────┼────────────────────────────────────────────┘     │
│              │                                                  │
│              ↓                                                  │
│   ┌───────────────────────────────────────────────────────┐     │
│   │                专用索引节点（同机器）                   │     │
│   │                                                       │     │
│   │   ┌─────────────┐    ┌─────────────┐                  │     │
│   │   │ 状态同步    │───→│  RPC 服务   │───→ 外部请求     │     │
│   │   │ (从Validator)│   │  (对外暴露)  │                  │     │
│   │   └─────────────┘    └─────────────┘                  │     │
│   │                                                       │     │
│   │   职责：对外提供 RPC，承受攻击和负载                    │     │
│   │   延迟：仍然是执行后立即获得（~400-600ms）              │     │
│   │                                                       │     │
│   └───────────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 核心原则

| 原则 | 说明 |
|------|------|
| **职责分离** | Validator 只做共识，索引节点负责 RPC |
| **风险隔离** | 攻击索引节点不影响共识 |
| **资源隔离** | RPC 负载不与共识竞争资源 |

## 4. 索引节点低延迟实现方案

### 4.1 方案 A：同机器部署 + 共享存储

```
┌─────────────────────────────────────────────────────────────────┐
│                      同一台服务器                                │
│                                                                 │
│   ┌─────────────────┐     ┌─────────────────┐                   │
│   │   Validator     │     │   索引节点       │                   │
│   │   进程          │     │   进程           │                   │
│   └────────┬────────┘     └────────┬────────┘                   │
│            │                       │                            │
│            └───────────┬───────────┘                            │
│                        ↓                                        │
│              ┌─────────────────┐                                │
│              │  共享 RocksDB    │  ← Validator 写入后            │
│              │  (状态存储)      │     索引节点立即可读            │
│              └─────────────────┘                                │
│                                                                 │
│   延迟增加：~几毫秒（本地存储读取）                               │
│   总延迟：400-600ms + 几毫秒 ≈ 400-600ms                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**优点**：
- 延迟最低
- 数据一致性好

**缺点**：
- 需要配置共享存储
- 进程间可能有锁竞争

### 4.2 方案 B：同机器 + 内网 RPC 订阅

```
┌─────────────────────────────────────────────────────────────────┐
│                      同一台服务器                                │
│                                                                 │
│   ┌─────────────────┐         ┌─────────────────┐               │
│   │   Validator     │  本地   │   索引节点       │               │
│   │                 │ ──────→ │                 │               │
│   │  RPC:127.0.0.1  │  订阅   │  RPC:内网暴露   │               │
│   └─────────────────┘         └─────────────────┘               │
│                                                                 │
│   Validator RPC 只监听 127.0.0.1                                 │
│   索引节点订阅本地 Validator，然后对外暴露                        │
│                                                                 │
│   延迟增加：~10-50ms（本地网络）                                  │
│   总延迟：400-600ms + 10-50ms ≈ 450-650ms                        │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**优点**：
- 实现简单
- 使用标准 RPC API

**缺点**：
- 略有延迟增加
- 本地网络开销

### 4.3 方案 C：本地事件转发（Unix Socket）

```rust
// Validator 配置：执行后转发事件到本地索引进程
impl SubscriptionHandler {
    pub fn process_tx(&self, tx_data: &TransactionData,
                      effects: &Effects, events: &Events) {
        // 原有逻辑：推送给本地订阅者
        self.event_streamer.try_send(event);

        // 新增：通过 Unix Socket 转发给同机器的索引进程
        if let Some(forwarder) = &self.local_indexer_forwarder {
            forwarder.send(events);
        }
    }
}
```

**优点**：
- 延迟最低（Unix Socket 开销极小）
- 无网络栈开销

**缺点**：
- 需要修改 Sui 源码
- 维护成本较高

## 5. 方案对比

| 方案 | 延迟 | 安全性 | 复杂度 | 推荐 |
|------|------|--------|--------|------|
| Validator 直接暴露 RPC | 400-600ms | 🔴 低 | 低 | ❌ 不推荐 |
| **同机器 + 共享存储** | **400-600ms** | **🟢 高** | **中** | **✅ 推荐** |
| **同机器 + 内网订阅** | **450-650ms** | **🟢 高** | **低** | **✅ 推荐** |
| 同机器 + Unix Socket | 400-600ms | 🟢 高 | 高 | ⚠️ 改源码 |
| 独立机器 Full Node | 2-4s | 🟢 高 | 低 | ⚠️ 延迟高 |

### 安全边界

| 组件 | 网络暴露 | 说明 |
|------|----------|------|
| Validator | 无 / 仅 127.0.0.1 | 不暴露任何外部接口 |
| 索引节点 | 内网 | 只暴露给内部服务 |
| 应用服务 | 可公网 | 通过负载均衡对外 |

### 防护措施

1. **Validator 防护**
   - 关闭外部 RPC 或仅监听 127.0.0.1
   - 防火墙只开放 P2P 端口
   - 共识私钥独立保管

2. **索引节点防护**
   - 内网访问，IP 白名单
   - 连接数限制
   - 请求频率限制

3. **网络隔离**
   - Validator 与应用服务不在同一网段
   - 通过索引节点中转

## 7. 总结

| 问题 | 答案 |
|------|------|
| Validator 直接暴露 RPC 安全吗？ | ❌ **有风险**，可能影响共识稳定性 |
| 推荐方案？ | ✅ **Validator + 同机器索引节点分离** |
| 延迟会增加吗？ | 几乎不会，同机器通信延迟 <50ms |
| 实现复杂度？ | 中等，需要部署两个进程 |
