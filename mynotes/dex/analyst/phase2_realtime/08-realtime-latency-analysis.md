# dex-realtime 延迟分析与方案选型

> 创建日期: 2026-02-05
> 更新日期: 2026-02-05（新增自建 Validator 方案、P2P 方案定位）
> 状态: 分析完成，推荐 Validator + 索引节点方案

## 1. 问题背景

### 1.1 原设计目标

dex-realtime 设计目标是实现 **<500ms** 的低延迟事件推送，用于：
- 实时订单簿更新
- 成交通知
- 持仓变化推送

### 1.2 发现的问题

当前方案使用 `sui_subscribeEvent` 连接 **Full Node**，实际延迟为 **2-4 秒**，与 Checkpoint 通道（dex-indexer）延迟相近，失去了 realtime 的核心价值。

---

## 2. Sui 事件推送机制分析

### 2.1 Validator vs Full Node 事件时机

```
                        Validator                    Full Node
                           │                            │
共识完成                    │                            │
   │                       │                            │
   ↓                       ↓                            │
本地执行完成          subscription_handler               │
   │                  .process_tx()                     │
   │                       │                            │
   │                       ↓                            │
   │              ⚡ 事件立即推送                         │
   │                  (~400-600ms)                      │
   │                       │                            │
   ↓                       ↓                            │
Checkpoint 构建            │                            │
   │                       │                            │
   ↓                       │                            ↓
Checkpoint 广播 ───────────┼──────────────────→ Full Node 同步
                           │                            │
                           │                            ↓
                           │                    ⚡ 事件推送
                           │                     (~2-4s)
```

### 2.2 关键源码位置

**Validator 事件推送**（`sui-core/src/authority.rs:3324-3326`）：
```rust
// 交易执行完成后，立即推送事件
self.subscription_handler
    .process_tx(certificate.data().transaction_data(), &effects, &events)
```

**Full Node 事件推送**（`sui-core/src/checkpoints/checkpoint_executor/mod.rs`）：
```rust
// 必须等 Checkpoint 同步后才推送
commit_index_updates_and_enqueue_to_subscription_service()
```

### 2.3 延迟对比

| 节点类型 | 事件推送时机 | 延迟 |
|----------|-------------|------|
| Validator | 本地执行完成后 | 400-600ms |
| Full Node | Checkpoint 同步后 | 2-4 秒 |

### 2.4 数据完整性

| 问题 | 答案 |
|------|------|
| 单节点能收到所有事件？ | ✅ 是，Sui 共识保证每个节点执行全部交易 |
| 连接 Full Node 会丢事件？ | ❌ 不会，Checkpoint 包含全部交易 |

## 3. 项目架构约束

### 3.1 共识后撮合架构

当前 Rust 撮合引擎是**共识后撮合**：

```
用户下单
   ↓
Sui 链（订单上链）
   ↓
共识排序 ─────────────────────── ~400ms
   ↓
Rust 引擎获取订单并撮合
   ↓
撮合结果提交链上
   ↓
共识确认 ─────────────────────── ~400ms
   ↓
Checkpoint ───────────────────── ~1-3s
```

### 3.2 延迟分析

| 阶段 | 延迟 | 累计 |
|------|------|------|
| 用户下单 → 订单共识 | ~400ms | 400ms |
| 引擎获取订单 | ~100ms | 500ms |
| 撮合计算 | <10ms | 510ms |
| 结果提交 → 共识 | ~400ms | 910ms |
| Checkpoint | ~1-3s | 2-4s |

## 4. 方案对比

### 4.1 方案概览

| 方案 | 延迟 | 需要 Validator？ | 开发周期 | 复杂度 | 推荐 |
|------|------|-----------------|----------|--------|------|
| Full Node 标准订阅 | 2-4s | ❌ | 0 | 低 | MVP |
| RPC 效果轮询 | 0.8-1.5s | ❌ | 1-2 周 | 低 | 备选 |
| **Validator + 索引节点** | **400-650ms** | **✅** | **1-2 周** | **中** | **✅ 推荐** |
| P2P 监听 Effects | 400-600ms | ❌ | 3-6 周 | 高 | 特殊场景 |
| 修改 Full Node | 400-600ms | ❌ | 4-8 周 | 很高 | 不推荐 |

### 4.2 方案详解

#### 方案 1：Full Node 标准订阅（当前方案）

```rust
let sui_client = SuiClientBuilder::default()
    .ws_url("wss://your-fullnode")
    .build()
    .await?;

let mut stream = sui_client.event_api().subscribe_event(filter).await?;
```

- **延迟**：2-4 秒
- **优点**：最简单，代码已有
- **缺点**：延迟与 Checkpoint 通道相近，价值有限

#### 方案 2：RPC 效果轮询（推荐）

```rust
struct EffectsPoller {
    sui_client: SuiClient,
    last_cursor: Option<TransactionDigest>,
}

impl EffectsPoller {
    async fn poll(&mut self) -> Vec<SuiEvent> {
        // 1. 查询最新交易
        let txs = self.sui_client
            .read_api()
            .query_transactions(filter, cursor, limit)
            .await?;

        // 2. 获取每笔交易的效果和事件
        let mut events = vec![];
        for tx in txs {
            let effects = self.sui_client
                .read_api()
                .get_transaction_block(tx.digest, options)
                .await?;
            events.extend(effects.events);
        }
        events
    }
}

// 主循环：每 100-200ms 轮询一次
loop {
    let events = poller.poll().await;
    for event in events {
        engine.process(event);
    }
    tokio::time::sleep(Duration::from_millis(100)).await;
}
```

- **延迟**：0.8-1.5 秒
- **优点**：不需要改节点，使用标准 RPC
- **缺点**：轮询有额外延迟

#### 方案 3：P2P 监听 CertifiedEffects

```
┌─────────────────────────────────────────────────────────────┐
│                 DEX Effects Monitor                          │
│                                                             │
│   ┌───────────────────────────────────────────┐             │
│   │  P2P 网络层                                │             │
│   │  - 加入 Sui P2P 网络                       │             │
│   │  - 订阅效果广播消息                        │             │
│   └───────────────────────────────────────────┘             │
│                       │                                     │
│                       ↓                                     │
│   ┌───────────────────────────────────────────┐             │
│   │  验证层                                    │             │
│   │  - 验证 Effects 签名                       │             │
│   │  - 确认 2f+1 签名                          │             │
│   └───────────────────────────────────────────┘             │
│                       │                                     │
│                       ↓                                     │
│   ┌───────────────────────────────────────────┐             │
│   │  事件提取层                                │             │
│   │  - 解析 Effects 数据                       │             │
│   │  - 过滤 DEX 事件                           │             │
│   └───────────────────────────────────────────┘             │
└─────────────────────────────────────────────────────────────┘
```

- **延迟**：400-600ms
- **优点**：接近 Validator 水平的低延迟
- **缺点**：需要深入 Sui P2P 协议，开发成本高

#### 方案 4：引擎直接推送

如果撮合引擎可以直接推送结果（不等链上确认）：

```
订单共识 (~400ms)
    ↓
Rust 引擎撮合
    ├──→ ⚡ 直接推送 Redis Stream（乐观结果）
    │      延迟：~500ms
    │
    └──→ 提交链上结算
           ↓
         Checkpoint（最终确认）
```

- **延迟**：~500ms（乐观推送）
- **优点**：最低延迟
- **缺点**：需要处理乐观更新与最终确认不一致的情况

## 5. dYdX 参考架构

dYdX v4 使用专用索引节点：

```
┌─────────────────────────────────────────────────────────────────┐
│                    dYdX v4 架构                                  │
│                                                                 │
│   Validator 1 ──┐                                               │
│   Validator 2 ──┼──→ Cosmos 共识                                │
│   Validator 3 ──┘         │                                     │
│                           ↓                                     │
│              ┌────────────────────────┐                         │
│              │   Indexer Full Node    │  ← 专用索引节点          │
│              │   - 不参与共识          │    区块确认后立即处理    │
│              │   - 同步全部数据        │                         │
│              └────────────────────────┘                         │
│                           │                                     │
│                           ↓                                     │
│              Kafka / Ender / Vulcan                             │
│                           │                                     │
│                           ↓                                     │
│              PostgreSQL + Redis + WebSocket                     │
└─────────────────────────────────────────────────────────────────┘
```

**关键差异**：
- dYdX 索引节点在区块确认后**立即处理**，不等额外周期
- Sui Full Node 需要等 Checkpoint 同步

## 7. 决策要点（更新）

### 7.1 已确认的条件

1. **自建 Validator**：✅ DEX 节点基于 Sui 扩展自建
2. **延迟目标**：<500ms
3. **安全要求**：Validator 不应直接暴露 RPC

### 7.2 推荐方案

| 场景 | 推荐方案 | 延迟 |
|------|----------|------|
| **生产环境** | **Validator + 同机器索引节点** | **400-650ms** |
| MVP 过渡 | Full Node 订阅 | 2-4s |
| 无 Validator 备选 | P2P 索引节点 | 400-600ms |

### 7.3 P2P 方案定位

P2P 方案当前**不需要投入**，原因：
- 自建 Validator 已满足低延迟需求
- P2P 方案复杂度高（3-6 周）
- 仅当未来无法使用 Validator 时才考虑

## 8. 自建 Validator 场景（推荐方案）

### 8.1 前提条件

由于 DEX 节点是基于 Sui 扩展自建的，拥有自己的 Validator 节点，可以采用最优方案。

### 8.2 推荐架构：Validator + 同机器索引节点

```
┌─────────────────────────────────────────────────────────────────┐
│                    Validator 服务器                              │
│                                                                 │
│   ┌──────────────┐        ┌──────────────┐                      │
│   │  Validator   │        │  索引节点     │                      │
│   │  进程        │───────→│  进程         │                      │
│   │              │ 本地   │              │                      │
│   │  RPC:关闭    │ 转发   │  RPC:内网    │                      │
│   │  或127.0.0.1 │        │  10.0.0.x    │                      │
│   └──────────────┘        └──────┬───────┘                      │
│                                  │                              │
└──────────────────────────────────┼──────────────────────────────┘
                                   │
                         内网 / 专用网络
                                   │
                                   ↓
┌──────────────────────────────────────────────────────────────────┐
│                    应用服务器                                     │
│                                                                  │
│   ┌────────────────┐     ┌────────────────┐                      │
│   │ Rust 撮合引擎  │────→│  Redis Stream  │────→ dex-ws          │
│   │ + dex-realtime │     └────────────────┘                      │
│   └────────────────┘                                             │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 8.3 安全考虑

**为什么不直接暴露 Validator RPC**：

| 风险 | 说明 |
|------|------|
| 共识影响 | RPC 负载可能导致共识响应延迟 |
| DDoS 攻击 | RPC 被攻击可能影响共识参与 |
| 资源竞争 | 大量订阅连接消耗资源 |
| 质押风险 | Validator 掉线可能被 slash |

**推荐做法**：Validator 专注共识，索引节点承担 RPC 服务。

### 8.4 延迟分析

| 组件 | 延迟 |
|------|------|
| 共识 + 执行 | 400-600ms |
| 本地转发（同机器） | <50ms |
| **总延迟** | **400-650ms** |

## 9. P2P 索引节点方案定位

### 9.1 方案适用场景决策树

```
                    是否自建 Validator？
                          │
              ┌───────────┴───────────┐
              ↓                       ↓
             是                      否
              │                       │
              ↓                       ↓
    ┌─────────────────────┐      需要低延迟吗？
    │ Validator + 索引节点 │              │
    │ (推荐方案)           │    ┌─────────┴─────────┐
    │                     │    ↓                   ↓
    │ 延迟：400-650ms     │   是                  否
    │ 复杂度：中           │    │                   │
    └─────────────────────┘    ↓                   ↓
                    ┌─────────────────────┐ ┌─────────────────┐
                    │ P2P 索引节点        │ │ Full Node 订阅  │
                    │ (备选方案)          │ │ (最简方案)      │
                    │                     │ │                 │
                    │ 延迟：400-600ms     │ │ 延迟：2-4s      │
                    │ 复杂度：高          │ │ 复杂度：低      │
                    └─────────────────────┘ └─────────────────┘
```

### 9.2 P2P 方案的独特价值

P2P 索引节点方案解决的是：**无法自建 Validator，但又需要低延迟** 的场景。

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   场景：不运行 Validator，但需要 <1 秒延迟                       │
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                    Sui P2P 网络                          │   │
│   │                                                         │   │
│   │   Validator 1 ──┐                                       │   │
│   │   Validator 2 ──┼──→ 广播 CertifiedEffects              │   │
│   │   Validator 3 ──┘           │                           │   │
│   │                             │                           │   │
│   │                             ↓                           │   │
│   │   ┌─────────────────────────────────────────────────┐   │   │
│   │   │          P2P 索引节点（旁听者）                  │   │   │
│   │   │                                                 │   │   │
│   │   │   - 不参与共识                                   │   │   │
│   │   │   - 不需要质押                                   │   │   │
│   │   │   - 监听 Effects 广播                            │   │   │
│   │   │   - 验证签名后推送事件                           │   │   │
│   │   │                                                 │   │   │
│   │   │   延迟：400-600ms（接近 Validator）              │   │   │
│   │   └─────────────────────────────────────────────────┘   │   │
│   │                                                         │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 9.3 P2P 方案何时值得投入？

| 条件 | 是否投入 P2P |
|------|-------------|
| 有自建 Validator | ❌ 不需要，用同机器索引节点 |
| 无 Validator + 可接受 1-2s 延迟 | ❌ 用 RPC 轮询 |
| 无 Validator + 必须 <1s 延迟 | ✅ 值得投入 |
| 未来可能自建 Validator | ⚠️ 等有 Validator 后再说 |

### 9.4 当前结论

**既然自建 Validator，P2P 方案可以暂时搁置**。

| 方案 | 当前状态 |
|------|----------|
| Validator + 索引节点 | ✅ **推荐采用** |
| P2P 索引节点 | ⏸️ 暂不需要 |
| Full Node 订阅 | 可作为 MVP 过渡 |
