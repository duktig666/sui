# Sui DEX Indexer 设计方案总结

> 基于 DYDX Indexer 设计思想，针对 Sui Checkpoint 延迟问题，设计双通道数据索引架构。

---

## 一、核心问题与解决方案

### 1.1 问题背景

**Sui Checkpoint 机制的延迟问题**：

- Sui 的数据最终性依赖 Checkpoint（每 ~3 秒生成一次）
- sui-indexer-alt 等标准索引方案基于 Checkpoint，延迟 3-5 秒
- 对于 DEX 交易场景，这种延迟**无法接受**

**DEX 数据延迟需求**：

| 数据类型 | 延迟要求 | Checkpoint 能否满足 |
|---------|---------|------------------|
| 订单簿 | <100ms | ❌ 不满足 |
| 最新成交 | <500ms | ❌ 不满足 |
| 仓位数据 | <1s | ⚠️ 勉强 |
| 历史订单 | 秒级 | ✅ 满足 |

### 1.2 解决方案：双通道数据摄取架构

借鉴 DYDX 的双通道设计思想：

```
┌─────────────────────────────────────────────────────────────────┐
│                     双通道数据摄取架构                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   DEX 引擎 / Sui 链上交易                                        │
│              │                                                   │
│              ├──────────────────┬───────────────────────────┐   │
│              │                  │                           │   │
│              ▼                  ▼                           │   │
│   ┌─────────────────┐   ┌─────────────────┐                │   │
│   │   FastPath      │   │   Checkpoint    │                │   │
│   │   (低延迟通道)   │   │   (批量通道)    │                │   │
│   │                 │   │                 │                │   │
│   │ • RPC 订阅      │   │ • sui-indexer   │                │   │
│   │ • <500ms 延迟   │   │ • 3-5s 延迟     │                │   │
│   │ • 乐观状态      │   │ • 最终状态      │                │   │
│   └────────┬────────┘   └────────┬────────┘                │   │
│            │                     │                          │   │
│            ▼                     ▼                          │   │
│        ┌───────┐           ┌───────────────┐               │   │
│        │ Redis │           │ TimescaleDB   │               │   │
│        │(实时) │           │ + ClickHouse  │               │   │
│        └───────┘           │ (持久化)      │               │   │
│                            └───────────────┘               │   │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

## 二、双通道架构：低延迟解决方案

### 2.1 FastPath 通道（低延迟）

**目的**：提供毫秒级的实时数据更新

**数据来源**：
- Sui 节点 RPC WebSocket 订阅 (`sui_subscribeTransaction`)
- 直接从 DEX 引擎获取订单更新（如果 DEX 引擎是链下服务）

**处理流程**：
```
Sui 节点 / DEX 引擎
        │
        │ 实时推送 (WebSocket / gRPC)
        ▼
FastPath Listener
        │
        │ 解析交易效果 / 订单事件
        ▼
Redis Stream (realtime-*)
        │
        ▼
Orderbook Processor
        │
        │ 更新缓存
        ▼
    Redis
    ├── 订单簿 (ZSET)
    ├── 订单状态 (HASH)
    └── 用户订单索引 (SET)
```

**特点**：
- **延迟**: <500ms
- **状态性质**: 乐观状态（`BEST_EFFORT_OPENED` / `BEST_EFFORT_CANCELED`）
- **存储目标**: **仅 Redis**，不写入数据库
- **可能回滚**: 是（可能被 Checkpoint 确认覆盖）

### 2.2 Checkpoint 通道（批量处理）

**目的**：提供数据完整性和持久化保证

**数据来源**：
- Checkpoint Store (RocksDB)
- 通过 sui-indexer-alt Pipeline 读取

**处理流程**：
```
Checkpoint Store
        │
        │ sui-indexer-alt Pipeline
        ▼
Checkpoint Processor
        │
        │ 解析 DEX 相关事件
        ▼
Kafka (checkpoint-data)
        │
        ▼
Trade / History Processor
        │
        │ 写入数据库
        ▼
┌───────────────────────────────┐
│  TimescaleDB                  │
│  ├── orders (订单记录)        │
│  ├── fills (成交记录)         │
│  ├── perpetual_positions     │
│  ├── candles (K线)           │
│  └── funding_rates           │
├───────────────────────────────┤
│  ClickHouse                   │
│  ├── 历史订单                 │
│  ├── 仓位快照                 │
│  └── 交易分析                 │
└───────────────────────────────┘
```

**特点**：
- **延迟**: 3-5 秒
- **状态性质**: 最终确定状态
- **存储目标**: TimescaleDB + ClickHouse（持久化）
- **可能回滚**: 否（Checkpoint 具有即时最终性）

### 2.3 两通道分工对比

| 维度 | FastPath (低延迟) | Checkpoint (批量) |
|-----|------------------|------------------|
| **延迟** | <500ms | 3-5s |
| **状态性质** | 乐观状态 | 最终确定 |
| **存储目标** | Redis | TimescaleDB + ClickHouse |
| **数据完整性** | 可能丢失 | 保证完整 |
| **用途** | 实时订单簿、订单状态 | 历史查询、K线、审计 |
| **是否写数据库** | ❌ 否 | ✅ 是 |

## 三、数据最终一致性保证

### 3.1 核心挑战

双通道架构面临的一致性问题：
1. **FastPath 数据可能不准确**：订单可能在链上被拒绝
2. **两通道数据可能不一致**：FastPath 更新快，Checkpoint 确认慢
3. **需要协调两个数据源**：用户看到的实时数据 vs 实际确认的数据

### 3.2 一致性保证机制

**核心原则：Checkpoint 数据是权威数据源 (Source of Truth)**

```
┌─────────────────────────────────────────────────────────────────┐
│                     数据一致性保证机制                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   时间线:                                                        │
│   ───────                                                        │
│                                                                  │
│   T0: 订单提交                                                   │
│        │                                                         │
│   T1: FastPath 收到交易效果 (~100ms)                             │
│        │                                                         │
│        └──► Redis 更新                                           │
│             订单状态: BEST_EFFORT_OPENED (乐观)                  │
│             订单簿: 新增价格层级                                  │
│                                                                  │
│   T2: Checkpoint 确认 (~3-5s)                                    │
│        │                                                         │
│        └──► TimescaleDB 写入 (最终状态)                          │
│             │                                                    │
│             └──► 同时更新 Redis                                  │
│                  订单状态: OPEN / FILLED / CANCELED              │
│                  (覆盖乐观状态)                                   │
│                                                                  │
│   ────────────────────────────────────────────────────────────   │
│                                                                  │
│   桥梁机制: StateFilledQuantumsCache                             │
│   ══════════════════════════════════                             │
│                                                                  │
│   Key: dex:filled:{order_id}                                    │
│   Value: 链上确认的成交量                                        │
│   写入: Checkpoint Processor (Trade Processor)                   │
│   读取: Orderbook Processor                                      │
│                                                                  │
│   作用:                                                          │
│   1. Checkpoint Processor 写入已确认成交量                       │
│   2. Orderbook Processor 读取，判断订单实际状态                  │
│   3. 发现不一致时，更新 Redis 订单状态                           │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 冲突解决策略

| 场景 | 处理方式 |
|-----|---------|
| **FastPath 订单被 Checkpoint 确认** | 状态从 `BEST_EFFORT_OPENED` → `OPEN`/`FILLED` |
| **FastPath 订单被 Checkpoint 拒绝** | 从 Redis 移除该订单，恢复订单簿 |
| **FastPath 成交量 vs Checkpoint 成交量** | 以 Checkpoint 为准，更新 `StateFilledQuantumsCache` |
| **FastPath 遗漏事件** | Reconciliation Service 定期对账，补充遗漏数据 |

### 3.4 乐观状态设计

借鉴 DYDX 的状态设计：

| 状态 | 含义 | 来源 |
|-----|------|------|
| `BEST_EFFORT_OPENED` | 订单已提交，待确认 | FastPath |
| `BEST_EFFORT_CANCELED` | 取消已提交，待确认 | FastPath |
| `OPEN` | 订单已确认，活跃中 | Checkpoint |
| `FILLED` | 完全成交 | Checkpoint |
| `CANCELED` | 已取消 | Checkpoint |

## 四、存储层设计

### 4.1 核心结论

**关键发现：FastPath 只写 Redis，不写数据库**

| 数据通道 | 存储目标 | 是否写入数据库 |
|---------|---------|--------------|
| FastPath (实时) | **Redis 仅缓存** | ❌ 否 |
| Checkpoint (批量) | **TimescaleDB + ClickHouse** | ✅ 是 |

**设计原理**：
- FastPath 数据是乐观的、可能回滚的，写入数据库会造成大量无效 I/O
- Redis 内存操作延迟低 (<1ms)，适合高频更新
- 数据库只存储 Checkpoint 确认的最终状态

### 4.2 三层存储架构

```
┌─────────────────────────────────────────────────────────────────┐
│                        三层存储架构                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  L1: Redis Cluster (实时层)                              │    │
│  │                                                          │    │
│  │  写入来源: FastPath                                       │    │
│  │  数据类型: 订单簿、活跃订单、仓位快照                      │    │
│  │  读取延迟: <1ms                                          │    │
│  │  用途: 实时行情、订单状态查询                             │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              │                                   │
│                              │ 异步同步                          │
│                              ▼                                   │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  L2: TimescaleDB (时序层)                                │    │
│  │                                                          │    │
│  │  写入来源: Checkpoint                                     │    │
│  │  数据类型: K线、成交记录、资金费率、订单                   │    │
│  │  读取延迟: <10ms                                         │    │
│  │  用途: 近期历史查询 (90天内)                              │    │
│  │  特性: Hypertable 自动分区、连续聚合                      │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              │                                   │
│                              │ 定期归档                          │
│                              ▼                                   │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  L3: ClickHouse (分析层)                                 │    │
│  │                                                          │    │
│  │  写入来源: Checkpoint                                     │    │
│  │  数据类型: 历史订单、仓位快照、交易分析                    │    │
│  │  读取延迟: <500ms                                        │    │
│  │  用途: 历史分析、OLAP 查询、永久存储                      │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 Redis 缓存结构

| 缓存 | Key 格式 | 数据类型 | 用途 |
|-----|---------|---------|------|
| 订单簿 | `dex:orderbook:{market}:{side}` | ZSET | 价格层级聚合 |
| 订单详情 | `dex:orders:{order_id}` | HASH | 订单完整数据 |
| 用户订单 | `dex:user_orders:{address}` | SET | 用户活跃订单 |
| 仓位 | `dex:positions:{address}:{market}` | HASH | 仓位快照 |
| 确认成交量 | `dex:filled:{order_id}` | STRING | 一致性桥梁 |

- **多 Indexer 全节点**: 主备切换，提高可用性

## 六、与 DYDX 方案对比

| 维度 | DYDX | Sui DEX | 差异说明 |
|-----|------|---------|---------|
| **链上数据源** | CometBFT 区块 | Sui Checkpoint | 不同共识机制 |
| **实时通道** | Off-chain Updates (to-vulcan) | FastPath (RPC 订阅) | Sui 无链下消息，通过 RPC 订阅 |
| **批量通道** | On-chain Events (to-ender) | Checkpoint Processor | 复用 sui-indexer-alt |
| **实时存储** | Redis | Redis | 相同 |
| **持久化存储** | PostgreSQL | TimescaleDB + ClickHouse | 针对时序和分析优化 |
| **一致性桥梁** | StateFilledQuantumsCache | StateFilledQuantumsCache | 相同设计思想 |

## 七、设计思想总结

### 7.1 核心设计原则

1. **双通道分离**: 实时性与数据完整性解耦
2. **存储层分离**: FastPath 只写缓存，Checkpoint 写数据库
3. **最终一致性**: Checkpoint 是权威数据源
4. **乐观更新**: FastPath 提供即时反馈，Checkpoint 提供最终确认

### 7.2 权衡取舍

| 选择 | 获得 | 代价 |
|-----|------|------|
| 双通道架构 | 低延迟 + 数据完整性 | 系统复杂度增加 |
| FastPath 只写 Redis | 减少无效 I/O | 数据可能暂时不一致 |
| StateFilledQuantumsCache | 一致性保证 | 额外的缓存维护 |
| 三层存储 | 性能分层优化 | 运维复杂度增加 |

### 7.3 适用场景

这套架构适用于：
- 需要实时订单簿展示的 DEX
- 高频交易场景
- 对延迟敏感的交易应用
- 同时需要历史数据分析的场景

不适用于：
- 简单的 DApp（sui-indexer-alt 足够）
- 对延迟不敏感的应用
- 不需要实时订单簿的场景
