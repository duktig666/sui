# CLOB 模块产品需求文档 (PRD)

## 1. 产品概述

### 1.1 产品定位

CLOB (中央限价订单簿) 是 Hermes DEX 的**核心交易引擎**,提供类似中心化交易所的订单簿交易体验,同时保持去中心化和透明性。

### 1.2 核心价值

**对交易者**:

- 限价单交易,精确控制成交价格
- 深度订单簿,提供充足流动性
- 透明的价格发现机制
- 多种订单类型,满足不同交易策略

**对系统**:

- 高性能匹配引擎,支持大量订单
- 自动清算机制,保护系统安全
- MEV 保护,确保公平交易

### 1.3 目标用户

- **普通交易者**: 使用限价单进行交易
- **专业交易者**: 使用高级订单类型 (条件单、TWAP)
- **做市商**: 提供流动性,赚取价差
- **套利者**: 利用价格差异获利

## 2. 功能需求

### FR-1: 订单放置

**需求描述**: 用户可以向订单簿放置不同类型的订单,等待匹配成交。

#### FR-1.1: 短期订单

**功能点**:

- 支持限价买单和卖单
- 订单在当前区块有效,区块结束后自动过期
- 适用于快速交易场景

**业务规则**:

- 订单必须指定价格和数量
- 价格必须符合交易对的最小价格变动单位
- 数量必须符合最小订单数量限制
- 账户必须有足够保证金支持订单

**验收标准**:

- 用户可以成功放置短期限价单
- 保证金不足时订单被拒绝
- 价格或数量不符合规则时订单被拒绝
- 订单在区块结束后自动从订单簿移除

**用户场景**:

场景 1: 快速买入 BTC

- 参与者: 普通交易者 Alice
- 前置条件: Alice 账户有 10,000 USDC
- 流程:
    1. Alice 查看 BTC-USD 订单簿,当前最佳卖价 50,100 USDC
    2. Alice 创建短期买单: 价格 50,000 USDC,数量 0.1 BTC
    3. 系统验证保证金充足 (需要 50,000 × 0.1 / 20 = 250 USDC,假设 20x 杠杆)
    4. 订单进入订单簿,等待匹配
    5. 如果当前区块内没有匹配,订单自动过期
- 后置条件: 订单匹配成功或自动过期

#### FR-1.2: 长期订单

**功能点**:

- 订单可以跨多个区块有效
- 支持 Good-Til-Time (GTT) 过期时间设置
- 适用于挂单等待成交的场景

**业务规则**:

- 订单必须指定过期时间 (GoodTilBlockTime)
- 过期时间必须在未来
- 订单在过期前持续有效,除非被取消或完全成交
- 系统定期检查并清理过期订单

**验收标准**:

- 用户可以成功放置长期限价单
- 订单可以在多个区块内持续匹配
- 到达过期时间后订单自动取消
- 用户可以在过期前手动取消订单

**用户场景**:

场景 2: 挂单等待目标价格

- 参与者: 专业交易者 Bob
- 前置条件: Bob 账户有 50,000 USDC
- 流程:
    1. Bob 认为 BTC 会跌到 48,000 USDC
    2. Bob 创建长期买单: 价格 48,000 USDC,数量 1 BTC,过期时间 24 小时后
    3. 系统验证保证金充足
    4. 订单进入订单簿
    5. 24 小时内,如果 BTC 价格跌到 48,000,订单匹配成交
    6. 如果 24 小时内未成交,订单自动过期
- 后置条件: 订单成交或过期

#### FR-1.3: 条件订单 (止损/止盈)

**功能点**:

- 订单在特定价格触发条件满足时自动激活
- 支持止损单 (Stop-Loss) 和止盈单 (Take-Profit)
- 帮助用户自动管理风险

**业务规则**:

- 订单必须指定触发价格和执行价格
- 止损单: 当市场价格 <= 触发价格时激活 (多头) 或 >= 触发价格 (空头)
- 止盈单: 当市场价格 >= 触发价格时激活 (多头) 或 <= 触发价格 (空头)
- 触发后订单转为普通限价单

**验收标准**:

- 用户可以成功放置条件订单
- 触发条件满足时订单自动激活
- 触发前订单不参与匹配
- 触发后订单按普通限价单匹配

**用户场景**:

场景 3: 止损保护

- 参与者: 交易者 Carol
- 前置条件: Carol 持有 1 BTC 多头仓位,开仓价 50,000 USDC
- 流程:
    1. Carol 担心 BTC 价格下跌
    2. Carol 创建止损卖单: 触发价格 48,000 USDC,执行价格 47,900 USDC,数量 1 BTC
    3. 系统监控市场价格
    4. 当 BTC 价格跌到 48,000 USDC 时,订单触发
    5. 订单转为限价卖单,价格 47,900 USDC
    6. 订单匹配成交,Carol 平仓,限制损失在 2,100 USDC
- 后置条件: 仓位平仓,避免更大损失

#### FR-1.4: 订单类型支持

**支持的订单类型**:

| 订单类型        | 说明                            | 使用场景              |
|-------------|-------------------------------|-------------------|
| 普通限价单       | 指定价格和数量                       | 标准交易              |
| Post-Only   | 只做 Maker,不立即成交                | 做市商提供流动性          |
| IOC         | 立即成交或取消 (Immediate-Or-Cancel) | 快速成交,不等待          |
| FOK         | 完全成交或取消 (Fill-Or-Kill)        | 大额订单,避免部分成交 (已废弃) |
| Reduce-Only | 只减少仓位,不增加                     | 平仓专用              |

**Reduce-Only 订单的特殊限制**:

Reduce-Only 订单仅支持以下组合:

- ✅ Short-Term + IOC + Reduce-Only
- ❌ Long-Term + Reduce-Only (不支持)
- ❌ Conditional + Reduce-Only (不支持)
- ❌ POST_ONLY + Reduce-Only (不支持)

**原因**: Reduce-Only 订单的目的是立即减少仓位,必须能够立即执行或取消,因此只能与 IOC 组合使用。

**验收标准**:

- 每种订单类型按预期行为执行
- Post-Only 订单如果会立即成交则拒绝
- IOC 订单立即匹配可成交部分,剩余取消
- FOK 订单已废弃,提交时返回错误
- Short-Term + IOC + Reduce-Only 订单可以成功放置
- 其他组合的 Reduce-Only 订单被拒绝,并返回清晰的错误消息

#### FR-1.5: TWAP 订单 (时间加权平均价格订单)

**需求描述**: TWAP (Time-Weighted Average Price) 订单允许用户将大额订单拆分为多个子订单,在指定时间内均匀执行,以减少价格冲击并获得接近平均价格的成交。

**功能点**:

- 支持大额订单拆分为多个子订单,在指定时间内均匀执行
- 减少价格冲击,获得接近平均价格的成交
- 支持价格容差控制,避免在不利价格成交
- 适用于大额交易场景

**业务规则**:

- 订单必须指定总时长 (Duration) 和执行间隔 (Interval)
- Duration 必须是 Interval 的倍数
- 生成的子订单数 = Duration / Interval
- 每个子订单在对应的时间间隔执行
- 支持价格容差 (PriceTolerance),超出容差时跳过该子订单
- 用户可以在任何时候取消 TWAP 订单,停止后续子订单执行

**参数约束**:

| 参数             | 最小值 | 最大值       | 单位  | 说明                 |
|----------------|-----|-----------|-----|--------------------|
| Duration       | 300 | 86,400    | 秒   | 订单执行总时长 (5分钟到24小时) |
| Interval       | 30  | 3,600     | 秒   | 每个子订单间隔 (30秒到1小时)  |
| PriceTolerance | 0   | 1,000,000 | ppm | 价格容差 (0% 到 100%)   |

**计算公式**:

**子订单数量计算**:

数学表达式:

```
子订单数 = Duration / Interval
每个子订单数量 = 总订单数量 / 子订单数
```

示例:

- 总订单: 10 BTC
- Duration: 3600 秒 (1小时)
- Interval: 600 秒 (10分钟)
- 子订单数 = 3600 / 600 = 6 个
- 每个子订单数量 = 10 / 6 ≈ 1.67 BTC

**价格容差验证**:

数学表达式:

```
|子订单执行价格 - TWAP目标价格| / TWAP目标价格 <= PriceTolerance / 1,000,000
```

示例:

- TWAP 目标价格: 50,000 USDC
- PriceTolerance: 10,000 ppm (1%)
- 允许价格范围: [49,500, 50,500] USDC
- 如果某个子订单执行时市场价格为 51,000 USDC,则该子订单被跳过

**验收标准**:

- 用户可以成功放置 TWAP 订单
- Duration 和 Interval 参数验证正确
- Duration 必须是 Interval 的倍数,否则订单被拒绝
- 子订单按预定时间间隔生成并执行
- 价格超出容差时子订单被跳过
- TWAP 订单可以提前取消,后续子订单不再执行
- 所有子订单执行完成后,TWAP 订单状态更新为"已完成"

**用户场景**:

场景 5: 大额买入减少冲击

- 参与者: 机构交易者 David
- 前置条件: David 账户有 1,000,000 USDC
- 流程:
    1. David 想买入 100 BTC,但担心单笔订单冲击价格
    2. David 创建 TWAP 买单:
        - 总数量: 100 BTC
        - 目标价格: 50,000 USDC
        - Duration: 7200 秒 (2小时)
        - Interval: 600 秒 (10分钟)
        - PriceTolerance: 10000 ppm (1%)
    3. 系统验证参数: 7200 / 600 = 12 个子订单,每个 8.33 BTC
    4. 系统每 10 分钟生成一个子订单,价格 50,000 USDC,数量 8.33 BTC
    5. 如果某个子订单执行时市场价格超出 50,000 × 1.01 = 50,500 USDC,跳过该子订单
    6. 2 小时后,David 完成大额买入,平均价格接近 50,000 USDC,价格冲击最小
- 后置条件: 完成大额买入,价格冲击最小化

**业务价值**:

- 机构交易者可以执行大额订单而不影响市场价格
- 减少滑点,获得更好的平均成交价格
- 自动化执行,无需人工盯盘
- 价格容差保护,避免在不利价格成交

#### FR-1.6: 订单数量限制

**需求描述**: 系统限制每个账户在每个交易对的每一侧(买或卖)可以同时持有的最大开放订单数量,以防止垃圾订单攻击并保护系统性能。

**业务规则**:

- 每个账户在每个交易对的每一侧(买或卖)最多可以有 **20 个开放订单**
- 开放订单包括:
    - 未成交的 Short-Term 订单
    - 未成交的 Long-Term 订单
    - 已触发但未成交的 Conditional 订单
    - 部分成交的订单
- 完全成交或过期的订单不计入限制
- 买单和卖单分别计数,互不影响

**限制说明**:

| 限制类型                | 数量                 |
|---------------------|--------------------|
| 每个账户每个交易对每侧的最大开放订单数 | 20                 |
| 买单和卖单分别计数           | 是                  |
| TWAP 订单是否计入限制       | 是,TWAP 主订单计为 1 个订单 |

**验收标准**:

- 账户开放订单数达到 20 时,新订单被拒绝
- 订单成交或过期后,可以放置新订单
- 买单和卖单分别计数,互不影响
- 错误消息清晰说明限制原因

**错误处理**:

- 错误码: `ErrOrderWouldExceedMaxOpenOrdersPerClobAndSide`
- 错误消息: "Order would exceed maximum open orders per CLOB and side (limit: 20)"

**用户场景**:

场景 6: 订单数量限制触发

- 参与者: 做市商 Eve
- 前置条件: Eve 在 BTC-USD 交易对已有 20 个买单
- 流程:
    1. Eve 尝试放置第 21 个买单
    2. 系统检查 Eve 在 BTC-USD 买侧的开放订单数
    3. 系统发现已达到 20 个订单限制
    4. 系统拒绝订单,返回错误: "Order would exceed maximum open orders per CLOB and side (limit: 20)"
    5. Eve 取消一个现有买单
    6. 系统允许 Eve 放置新买单
- 后置条件: Eve 维持 20 个买单

**业务解释**:
此限制用于:

- 防止垃圾订单攻击 (单个账户大量订单堵塞订单簿)
- 保护系统性能 (限制订单簿大小和匹配复杂度)
- 鼓励订单合并和优化 (用户应合并相近价格的订单)

#### FR-1.7: Builder Code 集成 (MEV-Burn 机制)

**需求描述**: 订单可以指定 Builder 地址和费用百分比,支持第三方构建器集成,用于 MEV-Burn 机制,减少 MEV 提取。

**功能点**:

- 订单可以指定 Builder 地址和费用百分比
- 支持第三方构建器集成 (如交易界面、机器人)
- 用于 MEV-Burn 机制,将 MEV 价值分配给 Builder
- Builder 费用从订单成交额中扣除

**业务规则**:

- Builder 地址必须是有效的 bech32 地址 (格式: `dydx1...`)
- Builder 费用百分比范围: 0 < fee <= 10,000 ppm (即 0% < fee <= 1%)
- Builder 费用从订单成交额中扣除,支付给 Builder 地址
- Builder 参数是可选的,不指定则无 Builder 费用

**参数说明**:

| 参数                | 类型     | 范围         | 说明                     |
|-------------------|--------|------------|------------------------|
| BuilderAddress    | string | bech32 地址  | Builder 钱包地址           |
| BuilderCodeFeePpm | uint32 | (0, 10000] | Builder 费用 (ppm),最高 1% |

**计算公式**:

**Builder 费用计算**:

数学表达式:

```
Builder费用 = 订单成交额 × BuilderCodeFeePpm / 1,000,000
```

示例:

- 订单成交额: 50,000 USDC
- BuilderCodeFeePpm: 5000 (0.5%)
- Builder 费用 = 50,000 × 5000 / 1,000,000 = 250 USDC
- 用户实际支付: 50,000 + 交易手续费 + 250 = 总成本
- Builder 收到: 250 USDC

**验收标准**:

- 订单可以指定有效的 Builder 参数
- Builder 费用正确计算并分配给 Builder 地址
- Builder 地址无效时订单被拒绝
- Builder 费用超出范围 (> 10,000 ppm) 时订单被拒绝
- Builder 费用在链上事件中正确记录

**用户场景**:

场景 7: 使用 Builder Code

- 参与者: 交易者 Frank,使用第三方交易工具 "TradingBot Pro"
- 前置条件: Frank 使用支持 Builder Code 的交易界面
- 流程:
    1. Frank 在 "TradingBot Pro" 中创建买单: 价格 50,000 USDC,数量 1 BTC
    2. 交易界面自动附加 Builder Code:
        - BuilderAddress: "dydx1abc..." (TradingBot Pro 开发商地址)
        - BuilderCodeFeePpm: 2000 (0.2%)
    3. 订单提交到链上,系统验证 Builder 参数有效
    4. 订单匹配成交,成交额 50,000 USDC
    5. Builder 费用计算: 50,000 × 0.002 = 100 USDC
    6. Frank 支付: 50,000 (仓位价值) + 交易手续费 + 100 (Builder 费用) = 总成本
    7. TradingBot Pro 开发商收到 100 USDC
- 后置条件: 交易完成,Builder 获得收益,激励第三方工具开发

**业务价值**:

- 支持第三方交易工具和界面集成
- 激励第三方开发者构建更好的用户体验
- MEV-Burn 机制:将 MEV 价值从验证者转移给 Builder,减少对用户的负面影响
- 透明的费用结构,用户可见 Builder 费用

### FR-2: 订单匹配

**需求描述**: 系统自动匹配买卖订单,按价格-时间优先原则执行成交。

#### FR-2.1: 价格-时间优先匹配

**功能点**:

- 价格优先: 最佳价格优先匹配
    - 买单: 价格高的优先
    - 卖单: 价格低的优先
- 时间优先: 相同价格下,时间早的优先
- 确定性匹配: 所有节点匹配结果一致

**业务规则**:

- 买单价格 >= 卖单价格时触发匹配
- 成交价格取 Maker 订单价格 (已在订单簿的订单)
- 部分成交支持: 订单可以分多次成交
- 匹配后立即更新账户余额和持仓

**验收标准**:

- 买卖订单正确匹配
- 价格-时间优先原则严格执行
- 成交价格符合预期 (Maker 价格)
- 成交后余额和持仓正确更新

**用户场景**:

场景 4: 限价单匹配成交

- 参与者: 买家 Alice,卖家 Bob
- 前置条件:
    - Alice 账户有 10,000 USDC
    - Bob 持有 1 BTC 多头仓位
    - 订单簿当前最佳买价 49,900,最佳卖价 50,100
- 流程:
    1. Alice 放置买单: 价格 50,100 USDC,数量 0.5 BTC (Taker)
    2. Bob 的卖单在订单簿: 价格 50,100 USDC,数量 1 BTC (Maker)
    3. 系统匹配 Alice 和 Bob 的订单
    4. 成交价格: 50,100 USDC (Maker 价格)
    5. 成交数量: 0.5 BTC
    6. Alice 获得 0.5 BTC 多头仓位,支付 25,050 USDC (含手续费)
    7. Bob 的卖单剩余 0.5 BTC,继续在订单簿
- 后置条件: Alice 持有 0.5 BTC,Bob 卖单剩余 0.5 BTC

#### FR-2.2: 部分成交

**功能点**:

- 订单可以分多次成交,每次成交一部分数量
- 完全成交后订单从订单簿移除
- 部分成交后订单剩余部分继续等待匹配

**业务规则**:

- 每次成交更新订单剩余数量
- 订单剩余数量 = 原始数量 - 已成交数量
- 完全成交时订单状态更新为"已完成"

**验收标准**:

- 订单可以分多次部分成交
- 每次成交后剩余数量正确
- 完全成交后订单移除

### FR-3: 订单取消

**需求描述**: 用户可以取消自己尚未完全成交的订单。

#### FR-3.1: 主动取消

**功能点**:

- 用户可以取消自己的订单
- 短期订单立即取消
- 长期订单从持久化存储删除

**业务规则**:

- 只能取消自己的订单
- 已完全成交的订单无法取消
- 部分成交的订单可以取消剩余部分
- 取消后释放占用的保证金

**验收标准**:

- 用户可以成功取消自己的订单
- 无法取消其他用户的订单
- 取消后订单从订单簿移除
- 保证金正确释放

**用户场景**:

场景 5: 取消挂单

- 参与者: 交易者 Alice
- 前置条件: Alice 有一个长期买单在订单簿,价格 48,000 USDC,数量 1 BTC
- 流程:
    1. Alice 发现市场趋势改变,不想等待成交
    2. Alice 提交取消订单请求
    3. 系统验证订单属于 Alice
    4. 系统从订单簿移除订单
    5. 系统释放订单占用的保证金 (2,400 USDC,假设 20x 杠杆)
- 后置条件: 订单取消,保证金释放

#### FR-3.2: 批量取消

**功能点**:

### FR-4: 清算机制

**需求描述**: 当用户账户保证金不足时,系统自动强制平仓,保护系统安全。

#### FR-4.1: 清算触发条件

**功能点**:

- 系统持续监控所有持仓账户的保证金水平
- 当账户总资产低于维持保证金要求时,触发清算
- 按账户风险程度排序,优先清算高风险账户

**计算公式**:

**维持保证金要求计算**:

数学表达式:

```
MaintenanceMarginRequirement = PositionValue × MaintenanceMarginRate
```

变量说明:

- **MaintenanceMarginRequirement**: 维持保证金要求 (USDC)
- **PositionValue**: 仓位价值 (USDC)
    - PositionValue = |PositionSize| × OraclePrice
    - PositionSize: 持仓数量 (正数为多头,负数为空头)
    - OraclePrice: 预言机价格 (USDC/BTC)
- **MaintenanceMarginRate**: 维持保证金率 (例如 3%)
    - 从流动性层级 (LiquidityTier) 配置获取
    - MaintenanceMarginRate = InitialMarginRate × MaintenanceFraction
    - MaintenanceFraction 通常为 50% (即维持保证金为初始保证金的 50%)

杠杆说明：

计算：

```
  Leverage = 1,000,000 / custom_imf_ppm
  custom_imf_ppm = 1,000,000 / Leverage
```



| 杠杆倍数 | custom_imf_ppm | IMF 百分比 |
| :------- | :------------- | :--------- |
| 10x      | 100,000 PPM    | 10%        |
| 20x      | 50,000 PPM     | 5%         |
| 5x       | 200,000 PPM    | 20%        |
| 50x      | 20,000 PPM     | 2%         |
| 100x     | 10,000 PPM     | 1%         |



计算示例:

- 假设用户余额5000U
- 假设用户持有 2 BTC 多头仓位
- 假设 BTC 价格 = 50,000 USDC
- 假设 InitialMarginRate = 5% (20x 杠杆)
- 假设 MaintenanceFraction = 50%
- PositionValue = 2 × 50,000 = 100,000 USDC
- MaintenanceMarginRate = 5% × 50% = 2.5%
- MaintenanceMarginRequirement = 100,000 × 2.5% = 2,500 USDC

**清算触发条件**:

数学表达式:

```
触发清算 if: TotalCollateral < MaintenanceMarginRequirement
```

变量说明:

- **TotalCollateral**: 账户总资产 (USDC)
    - TotalCollateral = USDCBalance + UnrealizedPnL
    - USDCBalance: USDC 余额
    - UnrealizedPnL: 未实现盈亏
        - UnrealizedPnL = (CurrentPrice - EntryPrice) × PositionSize (多头)
        - UnrealizedPnL = (EntryPrice - CurrentPrice) × PositionSize (空头)

计算示例 (清算触发):

- 假设用户 USDC 余额 = 3,000 USDC
- 假设用户持有 2 BTC 多头,开仓价 50,000 USDC
- 假设当前 BTC 价格 = 49,000 USDC (下跌)
- UnrealizedPnL = (49,000 - 50,000) × 2 = -2,000 USDC
- TotalCollateral = 3,000 + (-2,000) = 1,000 USDC
- MaintenanceMarginRequirement = 2 × 49,000 × 2.5% = 2,450 USDC
- 1,000 < 2,450 → **触发清算**

业务解释:

- 用户账户总资产只有 1,000 USDC,但维持仓位需要 2,450 USDC
- 账户处于高风险状态,系统强制平仓保护
- 清算后用户仓位清零,剩余资金返还用户

**业务规则**:

- 每个区块结束时检查所有持仓账户
- 按账户净资产排序,净资产最低的优先清算
- 清算时强制平仓,按市场价成交

**验收标准**:

- 保证金不足的账户被正确识别
- 清算按风险程度排序执行
- 清算后账户风险降低

**用户场景**:

场景 6: 保证金不足触发清算

- 参与者: 交易者 Dave
- 前置条件:
    - Dave 持有 5 BTC 多头,开仓价 50,000 USDC
    - Dave 账户余额 3,000 USDC
    - 当前 BTC 价格 49,500 USDC
- 流程:
    1. BTC 价格继续下跌到 49,000 USDC
    2. Dave 未实现亏损 = (49,000 - 50,000) × 5 = -5,000 USDC
    3. Dave 总资产 = 3,000 - 5,000 = -2,000 USDC (负数!)
    4. 系统检测到 Dave 账户保证金不足
    5. 系统生成清算订单,强制卖出 5 BTC
    6. 清算订单在订单簿匹配成交
    7. Dave 仓位清零,账户余额变为 0 (全部损失)
- 后置条件: Dave 仓位清零,损失全部保证金

#### FR-4.2: 清算执行

**功能点**:

- 系统自动生成清算订单
- 清算订单优先匹配,快速平仓
- 清算收益/损失分配给系统保险基金

**业务规则**:

- 清算订单以市场价立即成交
- 清算后账户仓位减少或清零
- 剩余资金返还用户 (如果有)
- 清算产生的损失由保险基金承担

**验收标准**:

- 清算订单成功生成并匹配
- 账户仓位正确减少
- 剩余资金正确返还

#### FR-4.3: 去杠杆机制 (Deleveraging)

**需求描述**: 当清算无法覆盖账户损失或市场进入最终结算时,系统强制平仓对手方持仓,分摊损失或平仓所有持仓。

**功能点**:

- 系统检测账户净资产为负或市场最终结算
- 自动查找反向持仓的账户
- 按盈利率排序选择去杠杆对象
- 强制平仓双方持仓,按特定价格结算
- 保护系统整体安全

**计算公式**:

**去杠杆触发条件 1: 负净抵押品 (Negative TNC)**:

数学表达式:

```
触发去杠杆 if: TNC < 0
```

变量说明:

- **TNC (Total Net Collateral)**: 总净抵押品
  - TNC = Account Balance + Unrealized PnL
  - Account Balance: 账户 USDC 余额
  - Unrealized PnL: 所有持仓的未实现盈亏总和

计算示例 (触发去杠杆):

- 假设用户 USDC 余额 = 1,000 USDC
- 假设用户持有 10 BTC 多头,开仓价 50,000 USDC
- 假设当前 BTC 价格 = 49,000 USDC (暴跌)
- Unrealized PnL = (49,000 - 50,000) × 10 = -10,000 USDC
- TNC = 1,000 + (-10,000) = **-9,000 USDC (负数!)**
- 负 TNC 触发去杠杆,账户已资不抵债

业务解释:

- 账户总资产为负,清算无法覆盖损失
- 必须强制平仓,并让对手方承担部分损失
- **去杠杆价格为破产价格 (使 TNC = 0 的价格)**

**去杠杆触发条件 2: 最终结算 (Final Settlement)**:

数学表达式:

```
触发去杠杆 if: Market.Status == FINAL_SETTLEMENT AND HasOpenPosition == true
```

变量说明:

- **Market.Status**: 市场状态
  - `FINAL_SETTLEMENT`: 市场永久关闭,停止交易
- **HasOpenPosition**: 账户是否有未平仓持仓

计算示例 (最终结算):

- 假设 BTC-USD 市场被决定关闭
- 市场状态变为 `FINAL_SETTLEMENT`
- 所有持有 BTC-USD 持仓的账户必须平仓
- **去杠杆价格为预言机价格**

业务解释:

- 市场关闭时所有持仓必须强制平仓
- 使用预言机价格作为公平结算价
- 即使账户健康也必须去杠杆

**破产价格计算**:

数学表达式:

```
BankruptcyPrice = EntryPrice - (AccountBalance / PositionSize)  (多头)
BankruptcyPrice = EntryPrice + (AccountBalance / PositionSize)  (空头)
```

变量说明:

- **BankruptcyPrice**: 破产价格,使账户净资产恰好为 0 的价格
- **EntryPrice**: 开仓价格
- **AccountBalance**: 账户 USDC 余额 (正数)
- **PositionSize**: 持仓数量 (绝对值)

计算示例 (多头破产价格):

- 假设用户持有 10 BTC 多头,开仓价 50,000 USDC
- 假设账户余额 1,000 USDC
- BankruptcyPrice = 50,000 - (1,000 / 10) = 50,000 - 100 = **49,900 USDC**
- 当价格跌到 49,900 时,账户恰好净资产为 0

业务解释:

- 破产价格是账户"生死线"
- 跌破破产价格,账户进入负资产状态
- 去杠杆时使用破产价格确保被去杠杆账户归零

**对手方选择逻辑**:

数学表达式:

```
PnL_Ratio = UnrealizedPnL / PositionValue

对手方排序: 按 PnL_Ratio 降序排列
```

变量说明:

- **PnL_Ratio**: 盈利率,盈利占仓位价值的比例
- **UnrealizedPnL**: 未实现盈亏
- **PositionValue**: 仓位价值 = |PositionSize| × CurrentPrice

计算示例:

假设需要去杠杆 10 BTC 空头 (卖出 10 BTC),寻找多头对手方:

| 账户 | 持仓量    | 开仓价    | 当前价    | PnL       | 仓位价值   | PnL Ratio | 去杠杆顺序 |
|------|-----------|-----------|-----------|-----------|------------|-----------|------------|
| A    | +5 BTC    | 48,000    | 50,000    | +10,000   | 250,000    | 4%        | **1st**    |
| B    | +3 BTC    | 49,000    | 50,000    | +3,000    | 150,000    | 2%        | **2nd**    |
| C    | +8 BTC    | 49,500    | 50,000    | +4,000    | 400,000    | 1%        | **3rd**    |

去杠杆分配:
- 账户 A: 去杠杆 5 BTC (盈利率最高)
- 账户 B: 去杠杆 3 BTC
- 账户 C: 去杠杆 2 BTC (剩余量)
- 总计: 5 + 3 + 2 = 10 BTC ✅

业务解释:

- 盈利最多的账户优先承担去杠杆
- 确保损失公平分摊
- 盈利率高的账户有能力承受

**业务规则**:

- 负 TNC 时立即触发去杠杆
- 最终结算时对所有持仓去杠杆
- 破产价格去杠杆:被去杠杆账户归零
- 预言机价格去杠杆:所有账户公平结算
- 对手方按盈利率从高到低排序
- 去杠杆后提现被暂时冻结,直到风险解除

**验收标准**:

- 负 TNC 账户被正确识别并去杠杆
- 最终结算时所有持仓被平仓
- 对手方选择符合盈利率排序
- 去杠杆价格正确(破产价格或预言机价格)
- 双方账户余额正确更新
- 提现门控在负 TNC 场景下正确触发

**用户场景**:

场景 7: 账户破产触发去杠杆

- 参与者:
  - 被去杠杆账户: Eve (多头,已破产)
  - 对手方账户: Frank (空头,盈利中)
- 前置条件:
  - Eve 持有 10 BTC 多头,开仓价 50,000 USDC,余额 2,000 USDC
  - Frank 持有 10 BTC 空头,开仓价 52,000 USDC,盈利中
  - 当前 BTC 价格 = 49,800 USDC
- 流程:
  1. Eve 的 TNC = 2,000 + (49,800 - 50,000) × 10 = 2,000 - 2,000 = 0 (临界)
  2. 价格继续跌到 49,700 USDC
  3. Eve 的 TNC = 2,000 + (49,700 - 50,000) × 10 = 2,000 - 3,000 = **-1,000 USDC (负数!)**
  4. 系统触发去杠杆流程
  5. 计算破产价格: 50,000 - (2,000 / 10) = **49,800 USDC**
  6. 系统查找空头对手方,发现 Frank (盈利率最高)
  7. 生成去杠杆成交:
     - Eve: 卖出 10 BTC @ 49,800 → 获得 498,000 USDC
     - Frank: 买入 10 BTC @ 49,800 → 支付 498,000 USDC
  8. 结算后:
     - Eve: 仓位清零,余额 = 2,000 + 498,000 - 500,000 (开仓成本) = **0 USDC** (归零)
     - Frank: 仓位清零,余额增加 (原本以 52,000 开仓,现在 49,800 平仓)
  9. Frank 承担了 Eve 的部分损失 (本应在 49,700 平仓更赚,但被迫在 49,800 平仓)
- 后置条件:
  - Eve 账户归零,离场
  - Frank 盈利减少,但避免了系统性风险

场景 8: 市场最终结算

- 参与者:
  - Alice: 持有 5 BTC 多头
  - Bob: 持有 3 BTC 空头
- 前置条件:
  - BTC-USD 市场被决定永久关闭
  - 预言机最终价格 = 50,000 USDC
- 流程:
  1. 治理提案通过,将 BTC-USD 市场状态设为 `FINAL_SETTLEMENT`
  2. 系统扫描所有持仓账户
  3. 发现 Alice (多头) 和 Bob (空头)
  4. 系统生成去杠杆成交:
     - Alice: 卖出 5 BTC @ 50,000 (预言机价格)
     - Bob: 买入 3 BTC @ 50,000 (预言机价格)
     - 剩余 2 BTC 由其他空头承接
  5. 所有持仓强制平仓
  6. 账户余额按预言机价格结算
- 后置条件: 所有账户持仓清零,市场关闭

业务解释:

- 大户可以获得更高的订单配额

- 激励用户保持充足资金

- 账户净资产越高,订单配额越多

- 超过配额的订单被拒绝

**验收标准**:

- 不同权益层级的账户获得不同配额
- 配额正确执行
- 大户不受过度限制

#### FR-5.3: 确定性匹配

**功能点**:

- 所有节点必须按相同顺序匹配订单
- 匹配结果完全一致
- 防止 MEV 操纵

**业务规则**:

- 订单按固定顺序排序 (价格-时间)
- 匹配算法确定性 (无随机性)
- 所有节点使用相同价格源 (预言机)

**验收标准**:

- 所有节点匹配结果一致
- 无法通过调整交易顺序获利
- 共识验证通过

### NFR-4: 系统限制与常量

**需求描述**: 系统定义了多个硬编码常量和限制,确保系统稳定性、安全性和性能。这些限制对用户行为和系统容量有重要影响。

#### 订单时间限制

| 限制类型                | 值      | 说明                                  |
|---------------------|--------|-------------------------------------|
| Short-Term 订单提前放置窗口 | 40 个区块 | Short-Term 订单最多可以提前 40 个区块放置,避免过早放置 |
| Long-Term 订单最大有效期   | 95 天   | GoodTilBlockTime 不能超过当前时间 + 95天     |

**业务影响**:

- Short-Term 订单提前放置窗口 (40 个区块,假设 1 秒/区块 ≈ 40 秒):用户可以提前约 40 秒提交订单,但订单不会立即执行
- Long-Term 订单最大有效期 (95 天):用户无法放置超过 95 天的长期订单,需要定期刷新

#### 批量操作限制

| 限制类型      | 值   | 说明                            |
|-----------|-----|-------------------------------|
| 批量取消最大订单数 | 100 | MsgBatchCancel 每次最多取消 100 个订单 |

**业务影响**:

- 用户需要批量取消超过 100 个订单时,需要分多次操作
- 防止单笔交易占用过多 Gas

#### TWAP 订单限制

| 参数                    | 最小值   | 最大值           | 说明                 |
|-----------------------|-------|---------------|--------------------|
| Interval (执行间隔)       | 30 秒  | 3600 秒        | 每个子订单间隔,太短会增加系统负担  |
| Duration (总时长)        | 300 秒 | 86400 秒       | 订单执行总时长,最长 24 小时   |
| PriceTolerance (价格容差) | 0     | 1,000,000 ppm | 允许的价格偏差,100% 表示无限制 |

**业务影响**:

- TWAP 最短 5 分钟 (300 秒),最长 24 小时 (86400 秒)
- 子订单间隔最短 30 秒,最长 1 小时
- Duration 必须是 Interval 的倍数

#### Builder Code 限制

| 参数                | 范围         | 说明                     |
|-------------------|------------|------------------------|
| BuilderCodeFeePpm | (0, 10000] | Builder 费用上限 1%,防止过高费用 |

**业务影响**:

- Builder 费用最高 1%,保护用户利益
- Builder 费用必须 > 0 (如果指定 Builder Code)

#### 条件订单限制

| 限制类型     | 值 | 说明                        |
|----------|---|---------------------------|
| 触发价格范围倍数 | 5 | 触发价格必须在预言机价格的 5倍最小价格变化范围内 |

**触发价格范围计算**:

数学表达式:

```
允许的触发价格上限 = 预言机价格 × (1 + 最小价格变化 × 5)
允许的触发价格下限 = 预言机价格 × (1 - 最小价格变化 × 5)
```

示例:

- 预言机价格: 50,000 USDC
- 最小价格变化: 0.01% (100 ppm)
- 倍数: 5
- 允许范围上限: 50,000 × (1 + 0.0001 × 5) = 50,000 × 1.0005 = 50,025 USDC
- 允许范围下限: 50,000 × (1 - 0.0001 × 5) = 50,000 × 0.9995 = 49,975 USDC
- 允许的触发价格范围: [49,975, 50,025] USDC

**业务影响**:

- 防止用户设置异常的触发价格 (如触发价格过高或过低)
- 确保条件订单在合理的价格范围内触发
- 触发价格超出范围时订单被拒绝

#### 订单数量与仓位限制

| 限制类型                | 值  | 说明       |
|---------------------|----|----------|
| 每个账户每个交易对每侧的最大开放订单数 | 20 | 防止垃圾订单攻击 |

**业务影响**:

- 做市商需要合并订单,无法在同一侧放置超过 20 个订单
- 买单和卖单分别计数,总共最多 40 个订单 (20 买 + 20 卖)

**验收标准**:

- 所有限制在代码中正确实施
- 超出限制的操作被拒绝,返回清晰错误消息
- 限制在文档中清晰说明,用户可以查询

### NFR-5: 可扩展性要求

**交易对扩展**:

- 支持动态添加新交易对
- 新交易对不影响现有交易对性能
- 支持至少 100 个交易对同时交易

**订单类型扩展**:

- 支持未来添加新订单类型
- 架构灵活,便于扩展

**验收标准**:

- 添加新交易对流程顺畅
- 新功能不破坏现有功能
- 扩展性测试通过

## 4. 用户场景

### 场景 7: 做市商提供流动性

**参与者**: 做市商 Market Maker (MM)

**前置条件**:

- MM 账户有 100,000 USDC
- BTC-USD 订单簿深度较浅

**流程**:

1. MM 分析市场,认为 BTC 合理价格在 50,000 USDC 左右
2. MM 放置多个 Post-Only 订单:
    - 买单: 49,900 USDC × 1 BTC
    - 买单: 49,800 USDC × 1 BTC
    - 卖单: 50,100 USDC × 1 BTC
    - 卖单: 50,200 USDC × 1 BTC
3. MM 的订单进入订单簿,提供流动性
4. 普通交易者的订单与 MM 的订单匹配
5. MM 赚取价差 (50,100 - 49,900 = 200 USDC 每 BTC)
6. MM 持续调整订单,维持流动性

**后置条件**: 订单簿流动性增加,价差缩小

**业务价值**:

- 做市商获得价差收益
- 系统获得充足流动性
- 用户获得更好的成交价格

### 场景 8: 套利者利用价差

**参与者**: 套利者 Arbitrager (Arb)

**前置条件**:

- Hermes DEX BTC 价格 50,200 USDC
- 其他交易所 BTC 价格 50,000 USDC
- Arb 账户有 100,000 USDC

**流程**:

1. Arb 发现价差机会 (200 USDC 每 BTC)
2. Arb 在其他交易所买入 10 BTC @ 50,000 USDC = 500,000 USDC
3. Arb 在 Hermes DEX 卖出 10 BTC @ 50,200 USDC = 502,000 USDC
4. Arb 套利收益 = 502,000 - 500,000 = 2,000 USDC (扣除手续费)
5. 价差缩小,Hermes 价格下降到 50,000

**后置条件**: 价格回归合理水平,市场更有效

**业务价值**:

- 套利者获得收益
- 价格保持与市场一致
- 提高市场效率

### 场景 9: 散户使用止损单

**参与者**: 散户交易者 Eve

**前置条件**:

- Eve 持有 2 BTC 多头,开仓价 50,000 USDC
- Eve 希望限制损失在 5%

**流程**:

1. Eve 计算止损价格: 50,000 × (1 - 5%) = 47,500 USDC
2. Eve 放置止损卖单:
    - 触发价格: 47,500 USDC
    - 执行价格: 47,400 USDC
    - 数量: 2 BTC
3. BTC 价格下跌到 47,500 USDC,止损单触发
4. 止损单转为限价卖单,价格 47,400 USDC
5. 订单匹配成交,Eve 平仓
6. Eve 损失 = (50,000 - 47,400) × 2 = 5,200 USDC (约 5.2%)

**后置条件**: 损失控制在可接受范围

**业务价值**:

- 用户风险管理工具
- 自动化止损,无需盯盘
- 保护用户资金

## 5. 业务指标

### 5.1 关键指标 (KPI)

**交易量指标**:

- 日均交易量 (USDC)
- 日均订单数量
- 日均成交笔数

**流动性指标**:

- 订单簿深度 (买卖价差 1% 内的总流动性)
- 平均价差 (Spread)
- 订单簿更新频率

**用户指标**:

- 日活跃交易者数量 (DAU)
- 月活跃交易者数量 (MAU)
- 用户留存率

**性能指标**:

- 订单成交率 (成交订单 / 总订单)
- 平均成交延迟
- 系统可用性

### 5.2 监控指标

**订单簿健康度**:

- 订单簿深度分布
- 价差变化趋势
- 订单堆积情况

**清算指标**:

- 清算触发频率
- 清算成功率
- 清算损失金额

**MEV 监控**:

- 可疑订单模式检测
- 价格操纵检测
- 异常交易检测

**系统性能**:

- 订单处理延迟
- 匹配引擎 CPU 使用率
- 内存使用情况

## 6. 术语表

| 术语          | 英文                        | 定义                                 |
|-------------|---------------------------|------------------------------------|
| 订单簿         | Order Book                | 所有未成交订单的集合,按价格排序                   |
| 限价单         | Limit Order               | 指定价格和数量的订单                         |
| 市价单         | Market Order              | 以当前市场价格成交的订单 (Hermes 不支持,用 IOC 替代) |
| 成交          | Fill                      | 买卖订单匹配的结果                          |
| Taker       | Taker                     | 主动成交的一方 (消耗流动性)                    |
| Maker       | Maker                     | 被动成交的一方 (提供流动性)                    |
| 保证金         | Margin                    | 用于支持仓位的资金                          |
| 清算          | Liquidation               | 强制平仓保证金不足的仓位                       |
| 价差          | Spread                    | 最佳买价和最佳卖价的差距                       |
| 深度          | Depth                     | 订单簿中某个价格档位的订单数量                    |
| 滑点          | Slippage                  | 预期价格和实际成交价格的差异                     |
| 止损单         | Stop-Loss Order           | 价格达到触发点时自动平仓的订单                    |
| 止盈单         | Take-Profit Order         | 价格达到目标时自动平仓的订单                     |
| Post-Only   | Post-Only Order           | 只做 Maker,不会立即成交的订单                 |
| IOC         | Immediate-Or-Cancel       | 立即成交或取消                            |
| FOK         | Fill-Or-Kill              | 完全成交或取消                            |
| Reduce-Only | Reduce-Only Order         | 只减少仓位,不增加仓位的订单                     |
| MEV         | Maximal Extractable Value | 通过操纵交易顺序获取的最大价值                    |
