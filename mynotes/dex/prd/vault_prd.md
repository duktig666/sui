# Vault 模块产品需求文档 (PRD)

## 1. 产品概述

### 1.1 产品定位

Vault (金库/流动性池) 模块是 Hermes DEX 的**自动化做市和流动性管理系统**,通过 Megavault 聚合流动性,自动在订单簿提供报价,为交易者提供稳定的流动性。

### 1.2 核心价值

**对流动性提供者 (LP)**:

- 无需专业知识,自动做市
- 份额机制,公平分配盈亏
- 分散风险到多个市场
- 提款灵活,可随时退出

**对交易者**:
- 订单簿始终有流动性
- 价差稳定,成交容易
- 深度充足,大额交易友好

**对系统**:
- 自动化流动性供给
- 降低运营成本
- 提高市场效率

### 1.3 目标用户

- **被动投资者**: 希望赚取收益但不想主动交易
- **小额投资者**: 资金不足以独立做市
- **风险分散者**: 希望分散到多个市场
- **交易者**: 受益于充足流动性

## 2. 功能需求

### FR-1: Megavault 存款

**需求描述**: 用户可以将 USDC 存入 Megavault,获得代表流动性池权益的份额。

#### FR-1.1: 存款流程

**功能点**:
- 用户存入 USDC 到 Megavault
- 系统计算并铸造份额给用户
- 份额代表用户在流动性池中的权益
- 存款立即生效,开始参与做市

**计算公式**:

**份额价值计算**:

数学表达式:
```
ShareValue = VaultEquity / TotalShares
```

变量说明:
- **ShareValue**: 单个份额的价值 (USDC/份额)
- **VaultEquity**: Vault 总净值 (USDC)
  - VaultEquity = TotalAssets - TotalLiabilities
  - TotalAssets: Vault 持有的 USDC + 未平仓合约的未实现盈亏
  - TotalLiabilities: Vault 的负债 (通常为 0)
- **TotalShares**: Megavault 总份额数

计算示例:
- 假设 Vault 总净值 = 1,000,000 USDC
- 假设 TotalShares = 500,000
- ShareValue = 1,000,000 / 500,000 = 2 USDC/份额

业务解释:
- 份额价值随 Vault 盈亏动态变化
- 盈利时份额价值上升,亏损时下降
- 新存款不影响现有持有者的份额价值

**存款份额计算**:

数学表达式:
```
SharesForDeposit = DepositAmount / ShareValue
```

变量说明:
- **SharesForDeposit**: 存款铸造的份额数
- **DepositAmount**: 存款金额 (USDC)
- **ShareValue**: 当前份额价值 (USDC/份额)

计算示例:
- 假设用户存款 10,000 USDC
- 假设当前 ShareValue = 2 USDC/份额
- SharesForDeposit = 10,000 / 2 = 5,000 份额

业务解释:
- 份额价值高时,相同金额获得更少份额
- 份额价值低时,相同金额获得更多份额
- 确保公平性,避免价值稀释

**业务规则**:
- 存款金额必须 > 0
- 存款立即转入 Vault,铸造份额
- 份额记录到用户账户
- 存款开始参与 Vault 盈亏

**验收标准**:
- 用户可以成功存款
- 份额计算正确
- 存款后立即获得份额

**用户场景**:

场景 1: 小额投资者存款
- 参与者: 小额投资者 Alice
- 前置条件:
  - Alice 有 5,000 USDC
  - Vault 当前份额价值 = 2 USDC/份额
- 流程:
  1. Alice 提交存款请求,存入 5,000 USDC
  2. 系统计算份额:
     - SharesForDeposit = 5,000 / 2 = 2,500 份额
  3. 系统转账 Alice 的 5,000 USDC 到 Vault
  4. 系统铸造 2,500 份额给 Alice
  5. Alice 开始参与 Vault 做市盈亏
- 后置条件: Alice 持有 2,500 份额,参与流动性提供

### FR-2: Megavault 提款

**需求描述**: 用户可以赎回份额,从 Megavault 提取 USDC,需要等待解锁期。

#### FR-2.1: 提款流程

**功能点**:
- 用户提交提款请求,指定赎回份额数
- 份额立即锁定,进入解锁期
- 解锁期结束后,用户可以提取 USDC
- 提款金额取决于解锁时的份额价值

**计算公式**:

**提款金额计算**:

数学表达式:
```
WithdrawAmount = WithdrawShares × ShareValue
ShareValue = VaultEquity / TotalShares (解锁时计算)
```

变量说明:
- **WithdrawAmount**: 提款金额 (USDC)
- **WithdrawShares**: 赎回的份额数
- **ShareValue**: 解锁时的份额价值 (USDC/份额)

计算示例:
- 假设用户赎回 5,000 份额
- 假设解锁时 Vault 总净值 = 1,100,000 USDC
- 假设解锁时 TotalShares = 500,000
- ShareValue = 1,100,000 / 500,000 = 2.2 USDC/份额
- WithdrawAmount = 5,000 × 2.2 = 11,000 USDC

业务解释:
- 提款金额取决于解锁时的份额价值
- 如果 Vault 在解锁期内盈利,用户获得更多
- 如果 Vault 在解锁期内亏损,用户获得更少
- 这是份额机制的核心:公平分配盈亏

**解锁期设计**:

数学表达式:
```
UnlockBlockHeight = CurrentBlockHeight + LockupPeriod
```

变量说明:
- **UnlockBlockHeight**: 解锁区块高度
- **CurrentBlockHeight**: 当前区块高度
- **LockupPeriod**: 锁定期长度 (区块数),通过治理配置

计算示例:
- 假设当前区块高度 = 1,000,000
- 假设锁定期 = 86,400 区块 (约 24 小时,假设 1 秒 1 区块)
- UnlockBlockHeight = 1,000,000 + 86,400 = 1,086,400
- 用户需要等到区块 1,086,400 才能提款

业务解释:
- 解锁期防止闪电贷攻击
- 给 Vault 时间调整仓位
- 保护其他 LP 利益

**业务规则**:
- 提款请求立即锁定份额,用户不能再交易
- 锁定的份额仍参与 Vault 盈亏 (直到解锁)
- 解锁后系统自动转账 USDC 给用户
- 解锁后销毁份额

**验收标准**:
- 用户可以提交提款请求
- 份额立即锁定
- 解锁后正确提款
- 提款金额计算正确

**用户场景**:

场景 2: 用户提款流程
- 参与者: 投资者 Bob
- 前置条件:
  - Bob 持有 10,000 份额
  - 当前份额价值 = 2 USDC/份额
  - 解锁期 = 24 小时
- 流程:
  1. Bob 提交提款请求,赎回 10,000 份额
  2. 系统立即锁定 Bob 的 10,000 份额
  3. 系统创建解锁记录:
     - 份额数: 10,000
     - 解锁时间: 24 小时后
  4. 24 小时内,Vault 做市盈利,份额价值上升到 2.1 USDC/份额
  5. 24 小时后,解锁时间到达
  6. 系统计算提款金额:
     - WithdrawAmount = 10,000 × 2.1 = 21,000 USDC
  7. 系统转账 21,000 USDC 给 Bob
  8. 系统销毁 Bob 的 10,000 份额
- 后置条件: Bob 提款 21,000 USDC,盈利 1,000 USDC

### FR-3: 自动做市

**需求描述**: Vault 自动在订单簿放置买卖订单,提供流动性,赚取价差。

#### FR-3.1: 订单自动刷新

**功能点**:
- 每个区块自动刷新 Vault 订单
- 取消旧订单,放置新订单
- 订单价格根据预言机价格动态调整
- 订单大小根据 Vault 净值动态调整

**计算公式**:

**订单报价计算**:

数学表达式:
```
BidPrice = OraclePrice × (1 - Spread / 2)
AskPrice = OraclePrice × (1 + Spread / 2)
```

变量说明:
- **BidPrice**: 买单价格 (Vault 愿意买入的价格,USDC)
- **AskPrice**: 卖单价格 (Vault 愿意卖出的价格,USDC)
- **OraclePrice**: 预言机价格 (市场中间价,USDC)
- **Spread**: 价差百分比 (例如 0.002 表示 0.2% 价差)

计算示例:
- 假设 BTC-USD OraclePrice = 50,000 USDC
- 假设 Spread = 0.002 (0.2% 价差)
- BidPrice = 50,000 × (1 - 0.002/2) = 50,000 × 0.999 = 49,950 USDC
- AskPrice = 50,000 × (1 + 0.002/2) = 50,000 × 1.001 = 50,050 USDC

业务解释:
- Vault 在中间价上下对称报价
- 价差越大,做市利润越高,但竞争力越低
- 价差越小,吸引更多交易,但利润越薄
- 价差通过治理配置,平衡收益和竞争力

**订单大小计算**:

数学表达式:
```
OrderSize = VaultEquity × PositionSizePct / OraclePrice
```

变量说明:
- **OrderSize**: 订单数量 (BTC 数量)
- **VaultEquity**: Vault 总净值 (USDC)
- **PositionSizePct**: 仓位大小百分比 (例如 0.05 表示 5%)
- **OraclePrice**: 预言机价格 (USDC/BTC)

计算示例:
- 假设 VaultEquity = 1,000,000 USDC
- 假设 PositionSizePct = 0.05 (5%)
- 假设 OraclePrice = 50,000 USDC/BTC
- OrderSize = 1,000,000 × 0.05 / 50,000 = 1 BTC

业务解释:
- 订单大小与 Vault 净值成正比
- PositionSizePct 控制单笔订单风险敞口
- 价格越高,相同资金购买的数量越少
- Vault 净值越大,订单越大,流动性越好

**业务规则**:
- 每个区块 EndBlocker 自动刷新订单
- 取消旧订单,放置新订单
- 订单价格跟踪预言机价格
- Vault 净值低于激活阈值时,停止做市

**验收标准**:
- 订单每个区块刷新
- 订单价格跟踪市场价格
- 订单大小合理
- 报价公式正确

**用户场景**:

场景 3: Vault 自动做市
- 参与者: Vault 系统,交易者 Carol
- 前置条件:
  - Vault 净值 = 1,000,000 USDC
  - BTC 预言机价格 = 50,000 USDC
  - 价差配置 = 0.2%
  - 仓位大小 = 5%
- 流程:
  1. 区块 N 开始,Vault EndBlocker 触发
  2. Vault 取消上一个区块的旧订单
  3. Vault 计算新订单:
     - BidPrice = 50,000 × 0.999 = 49,950 USDC
     - AskPrice = 50,000 × 1.001 = 50,050 USDC
     - OrderSize = 1,000,000 × 5% / 50,000 = 1 BTC
  4. Vault 放置新订单:
     - 买单: 49,950 USDC × 1 BTC
     - 卖单: 50,050 USDC × 1 BTC
  5. 交易者 Carol 看到订单簿,发现 Vault 的订单
  6. Carol 放置市价买单,与 Vault 的卖单匹配
  7. Vault 以 50,050 USDC 卖出 1 BTC
  8. Vault 赚取价差 (如果之前买入价格更低)
- 后置条件: Vault 提供流动性,赚取价差

### FR-4: 盈亏分配

**需求描述**: Vault 的做市盈亏公平分配给所有份额持有者。

#### FR-4.1: 盈亏分配机制

**功能点**:
- Vault 的盈亏自动反映在份额价值中
- 所有份额持有者按比例分享盈亏
- 无需手动分配,自动计算

**计算公式**:

**盈亏对份额价值的影响**:

数学表达式:
```
NewShareValue = (OldVaultEquity + PnL) / TotalShares
```

变量说明:
- **NewShareValue**: 盈亏后的份额价值 (USDC/份额)
- **OldVaultEquity**: 盈亏前的 Vault 总净值 (USDC)
- **PnL**: 盈亏金额 (USDC,正数为盈利,负数为亏损)
- **TotalShares**: 总份额数 (不变)

计算示例 (盈利):
- 假设盈利前 VaultEquity = 1,000,000 USDC
- 假设 TotalShares = 500,000
- 假设 Vault 做市盈利 = 50,000 USDC
- NewVaultEquity = 1,000,000 + 50,000 = 1,050,000 USDC
- NewShareValue = 1,050,000 / 500,000 = 2.1 USDC/份额 (从 2.0 上升)

计算示例 (亏损):
- 假设盈利前 VaultEquity = 1,000,000 USDC
- 假设 TotalShares = 500,000
- 假设 Vault 做市亏损 = 30,000 USDC
- NewVaultEquity = 1,000,000 - 30,000 = 970,000 USDC
- NewShareValue = 970,000 / 500,000 = 1.94 USDC/份额 (从 2.0 下降)

业务解释:
- 份额价值随 Vault 盈亏自动调整
- 所有持有者按份额比例分享盈亏
- 无需手动结算,透明公平

**用户收益计算**:

数学表达式:
```
UserPnL = UserShares × (NewShareValue - OldShareValue)
```

变量说明:
- **UserPnL**: 用户盈亏 (USDC)
- **UserShares**: 用户持有的份额数
- **NewShareValue**: 新份额价值
- **OldShareValue**: 旧份额价值

计算示例:
- 假设用户持有 10,000 份额
- 假设份额价值从 2.0 上升到 2.1
- UserPnL = 10,000 × (2.1 - 2.0) = 10,000 × 0.1 = 1,000 USDC
- 用户盈利 1,000 USDC

业务解释:
- 用户盈亏 = 份额数 × 份额价值变化
- 持有时间越长,份额价值波动影响越大
- 份额机制自动分配盈亏,无需手动操作

**业务规则**:
- 盈亏实时反映在份额价值中
- 提款时才实现盈亏 (赎回份额)
- 持有期间盈亏是账面盈亏

**验收标准**:
- 盈亏正确分配到份额价值
- 所有持有者公平分享
- 盈亏计算准确

## 3. 非功能需求

### NFR-1: 性能要求

**订单刷新性能**:
- 订单刷新延迟 < 区块时间
- 支持至少 50 个市场同时做市
- 订单放置延迟 < 1 秒

**存提款性能**:
- 存款处理延迟 < 区块时间
- 提款解锁检查延迟 < 5 秒

**验收标准**:
- 性能测试达到目标
- 做市不影响交易

### NFR-2: 安全性要求

**闪电贷防护**:
- 提款解锁期有效防止闪电贷攻击
- 份额价值锁定机制保护现有 LP

**资金安全**:
- 用户资金安全存储
- 盈亏分配公平透明
- 无资金丢失风险

**验收标准**:
- 闪电贷攻击测试无法成功
- 资金安全测试通过

### NFR-3: 可扩展性要求

**参数可配置**:
- 价差、仓位大小等参数可通过治理调整
- 解锁期可配置
- 激活阈值可调整

**市场扩展**:
- 支持动态添加新市场做市
- 新市场不影响现有市场

**验收标准**:
- 参数调整流程顺畅
- 扩展性测试通过

## 4. 用户场景

### 场景 4: 被动投资者赚取收益

**参与者**: 被动投资者 Dave

**前置条件**:
- Dave 有 50,000 USDC,不想主动交易
- Vault 当前份额价值 = 2 USDC/份额

**流程**:
1. Dave 存入 50,000 USDC 到 Megavault
2. Dave 获得 25,000 份额
3. Vault 自动做市 30 天
4. Vault 做市盈利 5% (通过价差和资金费率)
5. 份额价值上升到 2.1 USDC/份额
6. Dave 的份额价值 = 25,000 × 2.1 = 52,500 USDC
7. Dave 盈利 2,500 USDC (5%)
8. Dave 提交提款请求
9. 等待解锁期后,Dave 提款 52,500 USDC

**后置条件**: Dave 被动赚取 5% 收益,无需主动交易

**业务价值**:
- 降低做市门槛,吸引被动投资者
- 聚合流动性,提高市场效率
- 为系统提供稳定流动性

### 场景 5: 解锁期保护机制

**参与者**: 攻击者 Eve,正常 LP Frank

**前置条件**:
- Eve 尝试闪电贷攻击
- Frank 正常持有份额

**流程**:
1. Eve 尝试攻击:
   - 借入 1,000,000 USDC (闪电贷)
   - 存入 Megavault,获得大量份额
   - 操纵市场价格,使 Vault 短期盈利
   - 尝试立即提款,获取高价值份额
2. 系统防护:
   - Eve 的份额立即锁定,进入解锁期 (24 小时)
   - 闪电贷要求在同一交易内归还,Eve 无法等待
   - Eve 无法提款,攻击失败
   - Eve 被迫归还闪电贷,损失 Gas 费用
3. Frank 正常持有:
   - Frank 不受 Eve 攻击影响
   - 份额价值保持稳定

**后置条件**: 解锁期成功防止闪电贷攻击,保护正常 LP

**业务价值**:
- 解锁期防止快速套利攻击
- 保护长期 LP 利益
- 确保 Vault 稳定运行

### 场景 6: Vault 自动调整做市策略

**参与者**: Vault 系统

**前置条件**:
- BTC 价格波动剧烈
- Vault 持有 BTC 多头仓位

**流程**:
1. BTC 价格从 50,000 上涨到 55,000 (10% 上涨)
2. Vault 持有 20 BTC 多头仓位
3. Vault 未实现盈利 = 20 × (55,000 - 50,000) = 100,000 USDC
4. Vault 净值增加到 1,100,000 USDC
5. 下一个区块,Vault 刷新订单:
   - 新 OraclePrice = 55,000 USDC
   - 新 BidPrice = 55,000 × 0.999 = 54,945 USDC
   - 新 AskPrice = 55,000 × 1.001 = 55,055 USDC
   - 新 OrderSize = 1,100,000 × 5% / 55,000 = 1 BTC
6. Vault 订单价格自动跟踪市场价格
7. Vault 继续提供流动性

**后置条件**: Vault 自动调整策略,适应市场变化

**业务价值**:
- 自动化做市,无需人工干预
- 价格跟踪市场,始终提供合理报价
- 订单大小动态调整,风险可控

| 价差              | Spread               | 买卖价格之间的差距                                       |
| 仓位大小          | Position Size        | 单笔订单占 Vault 净值的比例                              |
| LP               | Liquidity Provider   | 流动性提供者,向 Vault 存款的用户                         |
