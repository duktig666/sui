# Prices 模块产品需求文档 (PRD)

## 1. 产品概述

### 1.1 产品定位

Prices (价格预言机) 模块是 Hermes DEX 的**去中心化价格数据源**,集成 Slinky Oracle,为系统提供准确、及时、抗操纵的价格数据,支撑清算、资金费率计算等核心功能。

### 1.2 核心价值

**对交易者**:
- 准确的价格数据,确保公平清算
- 去中心化价格源,抗审查
- 快速价格更新,减少滑点

**对系统**:
- 可靠的价格数据,保护系统安全
- 防止价格操纵,避免错误清算
- 多数据源聚合,提高准确性

### 1.3 目标用户

- **所有交易者**: 依赖准确价格进行交易和清算
- **系统模块**: CLOB、Perpetuals、Vault 等模块依赖价格数据
- **验证器节点**: 提交价格投票,参与共识

## 2. 功能需求

### FR-1: 价格数据获取

**需求描述**: 系统通过 Slinky Oracle 获取去中心化的价格数据,支持多个交易对。

#### FR-1.1: Slinky Oracle 集成

**功能点**:
- 集成 Slinky Oracle 协议
- 使用 Vote Extensions 机制提交价格
- 验证器节点独立获取价格并投票
- 价格在每个区块更新

**业务规则**:
- 每个验证器节点从外部交易所获取价格
- 验证器通过 Vote Extensions 提交价格投票
- 系统聚合所有验证器的价格投票
- 使用中位数作为最终价格

**验收标准**:
- 价格数据每个区块更新
- 价格聚合正确 (中位数)
- 所有验证器参与价格投票

**用户场景**:

场景 1: 价格更新流程
- 参与者: 验证器节点 V1, V2, V3, V4, V5
- 前置条件: BTC-USD 市场已创建
- 流程:
  1. 区块 N 开始,验证器准备提交 BTC 价格
  2. 每个验证器从外部交易所获取价格:
     - V1: 50,100 USDC
     - V2: 50,050 USDC
     - V3: 50,000 USDC
     - V4: 49,950 USDC
     - V5: 50,150 USDC
  3. 验证器通过 Vote Extensions 提交价格投票
  4. 系统聚合价格投票:
     - 排序: [49,950, 50,000, 50,050, 50,100, 50,150]
     - 中位数: 50,050 USDC
  5. 系统存储 BTC 价格 = 50,050 USDC
  6. 价格可用于清算、资金费率计算等
- 后置条件: BTC 价格更新为 50,050 USDC

#### FR-1.2: 价格市场配置

**功能点**:
- 每个价格市场有独立配置
- 配置包括交易对、精度、最小交易所数量等
- 支持动态添加新价格市场

**市场配置参数**:

| 参数              | 说明                          | 示例 (BTC/USD)        |
|------------------|------------------------------|---------------------|
| 市场 ID           | 唯一标识符                    | 1                   |
| 交易对            | 价格对名称                    | "BTC/USD"           |
| 价格精度          | 价格指数 (10^exponent)        | -5 (10^-5 = 0.00001)|
| 最小交易所数量    | 至少需要多少交易所价格         | 3                   |
| 最小价格变化      | 价格更新的最小变化百分比 (PPM) | 2,500 (0.25%)       |
| 交易所配置        | 支持的交易所列表               | Binance, Coinbase, Kraken |

**业务规则**:
- 市场配置通过治理设置
- 每个市场独立配置,互不影响
- 配置参数影响价格验证规则

**验收标准**:
- 可以创建新价格市场
- 配置参数正确应用
- 不同市场使用不同配置

### FR-2: 价格验证

**需求描述**: 系统验证价格更新的合理性,防止异常价格导致错误清算。

#### FR-2.1: Towards 条件验证

**功能点**:
- 验证新价格是否向指数价格靠拢
- 防止价格剧烈波动
- 保护用户免受异常价格影响

**计算公式**:

**Towards 条件** (价格向指数价格靠拢):

数学表达式:
```
Towards 条件: |newPrice - indexPrice| <= |oldPrice - indexPrice|
```

变量说明:
- **newPrice**: 新提交的价格 (USDC)
- **oldPrice**: 当前存储的价格 (USDC)
- **indexPrice**: 指数价格 (从订单簿计算,USDC)
  - indexPrice = (BestBidPrice + BestAskPrice) / 2

计算示例 (通过验证):
- 假设 oldPrice = 50,200 USDC
- 假设 indexPrice = 50,000 USDC (订单簿中间价)
- 假设 newPrice = 50,100 USDC
- oldDelta = |50,200 - 50,000| = 200 USDC
- newDelta = |50,100 - 50,000| = 100 USDC
- 100 <= 200 ✅ 通过验证 (新价格更接近指数价格)

计算示例 (未通过验证):
- 假设 oldPrice = 50,200 USDC
- 假设 indexPrice = 50,000 USDC
- 假设 newPrice = 50,300 USDC
- oldDelta = |50,200 - 50,000| = 200 USDC
- newDelta = |50,300 - 50,000| = 300 USDC
- 300 > 200 ❌ 未通过验证 (新价格偏离指数价格更远)

业务解释:
- Towards 条件要求价格逐步向订单簿价格靠拢
- 防止价格剧烈偏离市场
- 保护用户免受异常价格清算

**业务规则**:
- 新价格必须满足 Towards 条件或 Crossing 条件之一
- Towards 条件鼓励价格回归市场
- 如果两个条件都不满足,拒绝价格更新

**验收标准**:
- Towards 条件正确验证
- 异常价格被拒绝
- 合理价格通过验证

#### FR-2.2: Crossing 条件验证

**功能点**:
- 允许价格跨越指数价格,但限制跨越幅度
- 支持价格在震荡市场中灵活更新
- 防止价格锁死

**计算公式**:

**Crossing 条件** (价格跨越指数价格):

数学表达式:
```
tickSize = oldPrice × MinPriceChangePpm / 1,000,000
oldDelta = |oldPrice - indexPrice|
newDelta = |newPrice - indexPrice|

Crossing 条件: newDelta² × 1,000,000 <= oldDelta × tickSizePpm
即: newDelta <= sqrt(oldDelta × tickSize)
```

变量说明:
- **tickSize**: 价格变动单位 (USDC)
- **oldDelta**: 旧价格与指数价格的偏差 (USDC)
- **newDelta**: 新价格与指数价格的偏差 (USDC)
- **MinPriceChangePpm**: 最小价格变化百分比 (PPM),从市场配置获取

计算示例 (通过验证):
- 假设 oldPrice = 50,200 USDC
- 假设 indexPrice = 50,000 USDC
- 假设 newPrice = 49,900 USDC (跨越指数价格)
- 假设 MinPriceChangePpm = 2,500 (0.25%)
- tickSize = 50,200 × 2,500 / 1,000,000 = 125.5 USDC
- oldDelta = |50,200 - 50,000| = 200 USDC
- newDelta = |49,900 - 50,000| = 100 USDC
- 检查: 100² × 1,000,000 <= 200 × 2,500
        10,000,000,000 <= 500,000
        ❌ 条件不满足,需要重新计算

(注: 实际公式简化为 newDelta <= sqrt(oldDelta × tickSize))
- sqrt(oldDelta × tickSize) = sqrt(200 × 125.5) = sqrt(25,100) = 158.4 USDC
- newDelta = 100 USDC
- 100 <= 158.4 ✅ 通过验证

计算示例 (未通过验证):
- 假设 oldPrice = 50,200 USDC
- 假设 indexPrice = 50,000 USDC
- 假设 newPrice = 49,500 USDC (大幅跨越)
- oldDelta = 200 USDC
- newDelta = |49,500 - 50,000| = 500 USDC
- sqrt(200 × 125.5) = 158.4 USDC
- 500 > 158.4 ❌ 未通过验证 (跨越幅度过大)

业务解释:
- Crossing 条件允许价格跨越指数价格
- 但限制跨越幅度,防止剧烈波动
- 平衡价格灵活性和稳定性

**业务规则**:
- 新价格必须满足 Towards 或 Crossing 条件之一
- Crossing 条件适用于价格跨越指数价格的情况
- 跨越幅度受 tickSize 限制

**验收标准**:
- Crossing 条件正确验证
- 合理跨越通过验证
- 过度跨越被拒绝

**用户场景**:

场景 2: 价格验证保护
- 参与者: 验证器节点,交易者 Alice
- 前置条件:
  - BTC 当前价格 = 50,000 USDC
  - 订单簿指数价格 = 50,000 USDC
  - Alice 持有 1 BTC 多头,保证金充足
- 流程:
  1. 某个恶意验证器提交异常价格 = 45,000 USDC (下跌 10%)
  2. 系统验证价格:
     - oldPrice = 50,000 USDC
     - newPrice = 45,000 USDC
     - indexPrice = 50,000 USDC
     - 检查 Towards: |45,000 - 50,000| = 5,000 > |50,000 - 50,000| = 0 ❌
     - 检查 Crossing: newDelta = 5,000, sqrt(0 × tickSize) = 0
       5,000 > 0 ❌
  3. 系统拒绝异常价格,保持旧价格 50,000 USDC
  4. Alice 的仓位未被错误清算,保护成功
- 后置条件: 异常价格被拒绝,Alice 安全

### FR-3: 价格查询

**需求描述**: 系统提供价格查询接口,供其他模块和用户使用。

#### FR-3.1: 实时价格查询

**功能点**:
- 查询指定市场的当前价格
- 查询价格的更新时间
- 查询价格的精度和指数

**返回信息**:
- 市场 ID
- 当前价格 (USDC)
- 价格精度 (Exponent)
- 更新时间 (区块时间戳)

**验收标准**:
- 查询返回准确的价格
- 价格及时更新 (每个区块)
- 查询延迟 < 50ms

#### FR-3.2: 价格历史查询

**功能点**:
- 查询价格的历史变化
- 支持按时间范围查询
- 支持分页查询

**返回信息**:
- 价格时间序列
- 每个时间点的价格
- 价格变化趋势

**验收标准**:
- 历史价格准确
- 查询性能满足要求

## 3. 非功能需求

### NFR-1: 性能要求

**价格更新性能**:
- 价格更新延迟 < 区块时间 (1 秒)
- 支持至少 100 个价格市场同时更新
- 价格验证延迟 < 100ms

**查询性能**:
- 实时价格查询延迟 < 50ms
- 历史价格查询延迟 < 200ms

**验收标准**:
- 性能测试达到目标
- 价格更新不影响区块生成

### NFR-2: 准确性要求

**价格精度**:
- 价格精度 >= 6 位小数
- 中位数计算精度 >= 8 位小数
- 价格验证计算精度 >= 8 位小数

**数据完整性**:
- 每个区块必须有价格更新
- 价格不能丢失或跳跃
- 价格时间戳准确

**验收标准**:
- 精度测试通过
- 数据完整性测试通过

### NFR-3: 安全性要求

**防操纵**:
- 使用中位数聚合,防止单个验证器操纵
- 价格验证机制,防止异常价格
- 多数据源,提高可靠性

**容错性**:
- 支持部分验证器离线
- 至少 2/3 验证器在线即可更新价格
- 价格源故障时使用缓存价格

**验收标准**:
- 操纵攻击测试无法成功
- 容错测试通过

## 4. 用户场景

### 场景 3: 价格更新驱动清算

**参与者**: 交易者 Bob,验证器节点

**前置条件**:
- Bob 持有 5 BTC 多头,开仓价 50,000 USDC
- Bob 账户余额 3,000 USDC
- BTC 当前价格 50,000 USDC

**流程**:
1. BTC 市场价格下跌
2. 验证器节点获取新价格:
   - V1: 48,900 USDC
   - V2: 48,950 USDC
   - V3: 49,000 USDC
   - V4: 49,050 USDC
   - V5: 49,100 USDC
3. 系统聚合价格,中位数 = 49,000 USDC
4. 系统验证价格 (Towards 条件):
   - oldPrice = 50,000, newPrice = 49,000, indexPrice = 49,000
   - |49,000 - 49,000| = 0 <= |50,000 - 49,000| = 1,000 ✅
5. 价格更新为 49,000 USDC
6. CLOB 模块使用新价格检查清算:
   - Bob 未实现亏损 = (49,000 - 50,000) × 5 = -5,000 USDC
   - Bob 总资产 = 3,000 - 5,000 = -2,000 USDC (负数!)
   - 触发清算
7. Bob 的仓位被强制平仓

**后置条件**: 准确的价格数据驱动了及时的清算

**业务价值**:
- 准确价格保护系统安全
- 及时清算防止系统损失
- 去中心化价格源,公平透明

### 场景 4: 价格验证防止错误清算

**参与者**: 交易者 Carol,验证器节点

**前置条件**:
- Carol 持有 2 BTC 多头,保证金充足
- BTC 当前价格 50,000 USDC

**流程**:
1. 某个故障验证器获取错误价格 = 40,000 USDC (下跌 20%)
2. 验证器提交价格投票:
   - V1: 50,100 USDC
   - V2: 50,050 USDC
   - V3: 50,000 USDC
   - V4: 40,000 USDC (故障)
   - V5: 50,150 USDC
3. 系统聚合价格,中位数 = 50,050 USDC (忽略异常值)
4. 系统验证价格 (Towards 条件):
   - oldPrice = 50,000, newPrice = 50,050, indexPrice = 50,000
   - |50,050 - 50,000| = 50 <= |50,000 - 50,000| = 0 ❌
   - Towards 不满足,检查 Crossing
   - newDelta = 50, sqrt(0 × tickSize) = 0
   - 50 > 0,Crossing 也不满足
   (注: 实际上如果 indexPrice 略有偏差,可能通过验证)
5. 如果验证通过,价格更新为 50,050 USDC
6. Carol 的仓位未受影响,保护成功

**后置条件**: 中位数和价格验证保护用户免受异常价格影响

**业务价值**:
- 中位数抗操纵
- 价格验证防止异常
- 保护用户资金安全

## 5. 业务指标

### 5.1 关键指标 (KPI)

**价格更新指标**:
- 价格更新成功率 (每个区块)
- 价格更新延迟
- 验证器参与率

**价格准确性指标**:
- 价格与市场价差异 (平均)
- 异常价格拒绝次数
- 价格跳跃次数

### 5.2 监控指标

**价格健康度**:
- 验证器价格偏差分布
- 价格验证失败率
- 价格数据源可用性

**系统依赖**:
- 依赖价格的模块查询次数
- 价格查询延迟分布
