## FastPath 中为什么由客户端收集签名并提交 Certificate？

### 1. 职责划分：FastPath 不是“小号共识”，而是“本地验证 + 客户端聚合”

- **拥有对象交易的关键前提**：  
  - 每个输入对象只有一个所有者；  
  - 不存在跨用户的并发冲突；  
  - 各验证者可以**独立**判断该交易是否有效。  
- 在这种前提下，FastPath 的设计目标是：  
  - 验证者只做「本地验证 + 本地锁定」；  
  - **不再在验证者之间跑一套额外的排序/聚合协议**；  
  - 谁来聚合 2f+1 个签名，不影响安全性，只影响“谁主动发起网络轮次”。  
- 因此，Sui 选择让**客户端充当“轻量协调者”**：  
  1. 客户端向多个验证者并行广播 `Transaction`；  
  2. 每个验证者独立完成对象检查、签名校验、版本检查、锁定对象；  
  3. 客户端收集到 `2f+1` 个 `AuthoritySignature` 后，组装成 `Certificate`；  
  4. 客户端将 `Certificate` 提交给任意验证者执行。  

### 2. 性能视角：客户端聚合可以减少网络轮次，避免“验证者间再跑一轮”

如果不是客户端聚合，而是让某个验证者来聚合签名，大致会变成：

1. 客户端 → 验证者 A：发送交易；  
2. 验证者 A → 其他验证者：广播交易并收集签名；  
3. 其他验证者 → 验证者 A：返回签名；  
4. 验证者 A 组装 `Certificate`，执行或回传结果。

这相当于在验证者内部再引入一层“小共识风格”的协调：

- 多了一轮「A 与其他验证者之间」的请求-响应；  
- 引入了「谁是聚合者 / 主节点」的角色选择问题；  
- 聚合者自身如果变慢或出错，会放大延迟、变成**中心化瓶颈**。  

而现在的设计中：

- 客户端**直接与所有验证者并行通信**，天然利用全网带宽和并行度；  
- 网络轮次简化为：  
  - 轮次 1：客户端 ↔ 多个验证者（收集签名）；  
  - 轮次 2：客户端 ↔ 某个验证者（提交证书并执行）；  
- 因为不需要验证者之间再协调，FastPath 能做到你文档中测算的 **~200ms 延迟，TPS 20w+**。  

### 3. 协议与安全模型视角：避免在验证者内再设计一套“微型共识”

如果让验证者负责收集签名，会引入一系列协议层面的复杂度：

- **聚合者选择问题**：  
  - 是固定某个验证者？那它就变成性能和可用性的单点；  
  - 是轮换？那又要引入领导者选举、轮次、视图切换等逻辑，开始向完整共识协议靠拢。  
- **状态管理问题**：  
  - 每个待聚合交易需要在验证者侧维护「已收到哪些签名、还差多少」等状态；  
  - 出现超时、重发、重试时，清理和重建这些状态会很复杂。  
- **与共享对象路径的边界变模糊**：  
  - 共享对象交易已经有 Mysticeti 共识负责排序与提交；  
  - 如果在拥有对象路径里再搞一套“迷你共识 + 签名聚合”，会让两条路径在实现和心智模型上都变得更重、更难维护。  

当前方案下的安全属性则非常干净：

- 任何一方（客户端或恶意节点）都**无法伪造** `2f+1` 签名；  
- 只要有 ≥2f+1 个诚实验证者，它们签过的交易就可以被任何人构造出合法 `Certificate` 并提交执行；  
- 客户端只是“搬运和拼装签名”的角色，对安全性不构成额外假设。  

### 4. 工程实践视角：客户端通常是“服务端 / 钱包后端”，并不是真的浏览器

从你 DEX 场景的角度看，“客户端收集签名、构造 Certificate” 并不意味着：

- 浏览器里的前端 JS 去直接跟全网验证者打交道；  
- 终端用户自己管理复杂的签名缓存与重试逻辑。

在真实部署中，更常见的形态是：

- **钱包后端 / DEX 后端服务**：  
  - 使用 `sui-sdk` 或等价的 RPC 封装；  
  - 负责向多个验证者广播交易、收集签名、构造 `Certificate`、重试错误等；  
  - 对前端暴露的只是一个“下单/转账”的简单 API。  
- 这样做的好处是：  
  - 核心链上协议保持简单：验证者只需实现“本地验证 + 执行”；  
  - 上层应用可以根据自身需求（延迟、容错、观测）在“如何选验证者、如何并发收集签名”上做优化。  

### 5. 对 DEX 设计的启示

- **如果你在 Sui 上做 DEX 并想充分利用 FastPath**：  
  - 所有走 FastPath 的交易（例如用户自托管资产的简单转移、挂单的某些辅助操作）都可以依赖“客户端聚合签名”的模式；  
  - 你可以在 DEX 的后端服务里实现一层「签名收集器」，对前端完全屏蔽细节。  
- **如果你在设计自己的执行层 / App 链**：  
  - 想要获得类似 FastPath 的低延迟特性，可以沿用这一模式：  
    - 验证者只做本地验证和锁定；  
    - 由客户端 / 网关服务做签名聚合与证书构造；  
  - 避免在验证者之间再跑一套“小共识”，把真正需要全局顺序的场景交给统一的共识层处理。  

### 简短回答（结论）
为什么是客户端收集签名和提交 Certificate？核心原因有三点：
1. FastPath 不是“简化版共识”，而是“本地验证 + 客户端聚合”
拥有对象交易天然无并发冲突，验证者可以各自独立验证并给出签名，不需要验证者之间再跑一轮协调协议；让客户端充当“签名聚合者”，只是负责把 2f+1 个独立签名拼成 Certificate，不改变安全模型。
2. 从性能来看，客户端聚合可以减少网络轮次，避免在验证者之间再跑一层“小共识”
当前设计中只有两轮：
客户端 ↔ 多个验证者：广播交易并收集签名；
客户端 ↔ 任一验证者：提交 Certificate 执行；
如果改成验证者聚合，就要多一轮“聚合者验证者 ↔ 其他验证者”的交互，相当于额外的小共识，增加延迟、引入中心化聚合者瓶颈，FastPath 很难做到 ~200ms / 20w+ TPS。
3. 从协议与工程复杂度来看，客户端聚合更简单、更干净
让验证者聚合，需要解决“聚合者选举、状态管理、超时与重试”等问题，本质上在验证者内再造一套微型共识，破坏了 FastPath 的轻量性，也和共享对象那条共识路径职责边界变得模糊。
在实际系统里，“客户端”通常是钱包后端 / DEX 后端服务，而不是浏览器前端，对终端用户透明；验证者逻辑保持简单（本地验证 + 执行），上层应用可以根据自己对延迟和可靠性的需求，自由实现签名收集与重试策略。
